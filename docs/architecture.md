# Resonant architecture

Resonant is an always-on personal agent harness that runs as a daemon on a dedicated home Mac mini. It takes events in from iMessage, Slack, webhooks, schedules and extensions. A local LLM (the **brain**) reads every message, answers what it can and routes the rest to tools. Engineering and ops work goes to **Claude workers** it spawns, which run like the owner at the keyboard, by default with no sandbox (`runner.guard: off`; a **thin guard** that protects only Resonant is the `thin` option) ([`employee-plan.md`](employee-plan.md)). Every side effect of Resonant's own tools passes a policy gate; workers act on standing trust and ask only for something net new. Product logic lives in **extensions**, which are separate repos that plug in through `resonant.yaml`.

For an interactive version, open [`architecture.html`](architecture.html), which has a clickable graph, the lifecycle, the approval flow, the roadmap and the trust model. The frozen contracts are in [`interfaces.md`](interfaces.md).

## Shape

```
 iMessage (owner) ─────┐ principal map   ┌── runner=local : router (fast path · approvals · relay)
 Slack (owner+cofndr) ─┤ (identity →     │                  → brain: qwen3 (≤3 tool calls)
 Webhook (HMAC, TBD) ──┼─> principal) ─> events ─> Loop ─┤── runner=claude: Claude workers (≤4), each in a
 Scheduler / ext emit ─┤                 (event+tick)     │     worktree of ~/code/<repo> or a scratch dir,
 Worker events ────────┘                                  │     guard off by default; resonant ask/note/check
                                                          │     over a per-run socket → worker desk
                                                          └── runner=cu    : computer use (Phase 9)
   worker desk ── ask ──> relay ──> owner "R4 asks: …" ──> reply routed back to R4
               ── check ─> trust rules (ok | ask: yes / yes always / no)
   run events ──> reports: now (text) | digest (hourly pulse "Workers:" rollup, with github PRs)
                       Permissions(principal, extension) → Gate(level, scope, approvers) → Executor
                         (idempotency key, Keychain secrets, audit: requested_by / approved_by)
   Store (SQLite WAL): tasks · events · approvals · runs · run_questions · trust_rules · repos · pulse_items · audit_log · kv
   FastAPI on 127.0.0.1 (loopback only)     │   watchdog thread + dead-man ping   │   LaunchAgents
```

- **One asyncio process** runs the loop and the local API. Extensions, MCP servers, Claude workers and computer-use workers run as child processes, so a crash never takes down the core.
- **launchd supervises it** as a per-user LaunchAgent (`gui/<uid>`). Messages.app, computer use and the login Keychain all need the GUI session. Ollama has its own LaunchAgent (`OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_CONTEXT_LENGTH=32768`). Extension jobs run on the daemon's scheduler. Critical jobs with their own LaunchAgents (through `resonant job-guard`, which honors the kill switch) are deferred ([`extensions.md`](extensions.md#critical-job-launchagents-and-job-guard)).
- **There are no public ports.** The API binds to loopback only, and config validation enforces it. iMessage reads `chat.db` locally. Slack uses Socket Mode. Inbound webhooks have no transport yet: with no tailnet, how third parties reach `/hooks` without a public port is an open follow-up (owner design: [PER-265](https://linear.app/doriapp/issue/PER-265)). They must still be HMAC-signed. CI status is polled, never pushed to us. Remote status goes through a push-only, read-only status relay (the Mini pushes to Supabase; a Fly app serves the dashboard and the dead-man checker), so this rule stays: see [`dashboard-plan.md`](dashboard-plan.md) and go-live step 15.
- **Runtime state** lives in `~/.resonant/`: `config.yaml`, `principals.yaml`, `resonant.db`, `backups/` (BK-1: `daily/` copies of the store and `pre-restore/` ones, 0700), `logs/`, `evals/`, `extensions/` (approved read-only copies), `ext-data/` (each extension's writable state), `runner/` (daemon-only mirrors, transcripts) and `run-secrets/` (both follow `RESONANT_HOME` unless `runner.mirror_dir`/`runner.secrets_dir` are set, PER-271: a daemon run with a non-default `RESONANT_HOME` re-clones its mirrors there). Workers write elsewhere: the owner's checkouts and their worktrees and scratch dirs in `~/code` (`runner.code_dir`), and run dirs (the session's tmp and credentials, and its home under `runner.guard: thin`) in `~/resonant-runs` (`runner.work_dir`). With the guard off (the default) a worker's `HOME` is the owner's.
- **Instances (PER-297, Phase 8).** One checkout can run more than one daemon as the same user, each an instance with its own `instance.name`. `resonant/instance.py` derives everything that would collide from the name: the home (`~/.resonant` or `~/.resonant-<name>`), the LaunchAgent label (`com.resonant.daemon` or `com.resonant.<name>.daemon`), the Keychain service (`resonant` or `resonant-<name>`) and the worker dirs (`~/<name>/runs`, `~/<name>/code`). `api.port` is set per instance (Cori: 7778) and install refuses a bound one. The CLI targets an instance with `--instance <name>` or `RESONANT_INSTANCE`, and refuses a home whose config names another instance. With no `instance:` block every name is the pre-instance one, so personal Resonant doesn't move. Contract: [`interfaces.md`](interfaces.md#instances-resonantinstance-per-297); example config: `config/cori.example.yaml`. **Two daemons, one checkout (PER-290).** Every instance runs from the same checkout and venv, so one deploy restarts them all: personal `/update` pulls and syncs once, backs every store up when the pull adds a migration, restarts each installed sibling (found from its LaunchAgent plist, `instance.siblings`) with the restart marker in its own store, then itself. Cori has `ops.self_update: false` (no code deploys) and `runner.self_repo: false` (no `resonant` repo), and the shared agents (Ollama, keep-awake) are personal Resonant's alone. Personal `/kill` pauses every sibling through the sibling's own CLI (`resonant pause --by sibling:resonant`), and `/resume` lifts only that pause. Neither brain's shell may write any instance's home. **Notify-owner bridge (PER-301).** Personal Resonant stays the only process that touches Messages. An instance with `notify_owner:` (Cori) forwards every urgent item (an extension's urgent report, a health incident and its recovery, a run's urgent failure) to personal Resonant's loopback `POST /api/notify-owner` (bearer token `core/notify_token_<name>` in personal's Keychain), which stores it as a pulse item of source `instance:<name>` and texts it through the usual urgent path (`[Cori] 🔴 <title>` once, the 20-an-hour cap, pause, `/ext mute cori`), recording it in `system_texts` so its brain can answer about it. Cori keeps a small outbox with backoff and DMs the owner once on her own channel while personal is unreachable or refuses her token. Contract: [`interfaces.md`](interfaces.md#notify-owner-bridge-resonantnotify_owner-per-301).

## Employee mode

The owner texts Resonant like an employee ([`employee-plan.md`](employee-plan.md); it replaced the remaining waves of [`repos-plan.md`](repos-plan.md) and the strict sandbox of [`phase5a-plan.md`](phase5a-plan.md), both now historical).

## Task lifecycle

```
queued ──dispatch──> running ──Continue──> queued
                        │──Wait(reason, wake_at?)──> waiting ──event or wake_at──> queued
                        │──Done──> done
                        │──Fail(retryable, attempts left)──> queued (backoff or retry_at; events kept)
                        └──Fail(final) / cancel ──> failed / cancelled
wait reasons: approval · human_reply (also a worker question: run wait_reason=question) · usage_reset · ci · veto (reserved; veto windows are deferred)
```

- One transaction per step commits the outcome, the checkpoint and the consumed events together.
- A crash mid-step leaves the task `running` with its last checkpoint and its events unconsumed. On the next start it is requeued, and the crash counts as an attempt, so crash loops are bounded. A graceful shutdown requeues without using an attempt.
- Runners save anything a retry must not lose with `ctx.save(...)`. For example, `claude_session_id` is saved as soon as the session starts.
- Side effects are idempotent through `executions`. A key that succeeded is never re-run. A key that started but never finished is reported as ambiguous instead of being retried blindly.

## Scheduling and priority

- Priority is set by lane and principal, never by the model: **on-call 0 < owner 1 < co-founder 2 < background 3**.
- At most `max_parallel` steps run at once, and the last parallel slot is kept for on-call.
- Claude sessions also need a slot from `SlotPool`. The cap defaults to 5, with 1 slot reserved for on-call.
- A slot is held only while a step is in flight. A session that needs to wait (approval, human reply, usage reset, CI) returns `Wait`, which frees the slot, and resumes later by `claude_session_id`. Running sessions are never preempted.
- Usage limits are not throttled ahead of time. When a limit is hit, the affected tasks are parked with `wait_reason=usage_reset` and `wake_at`, they resume automatically, and you are notified once.

## Tool core

Every tool call, whoever picked it, goes through one package: `resonant/toolcore/` (TC-1). The callers are the local runner (slash commands, pinned calls), the brain's hand-off, the media runner, the Claude bridge (MCP), the job and watch runners and the approval resume of a pinned call; each builds a `CallScope` (task, principal, trace, step, call index, origin, the checkpoint and its `save`, the report lines of the changes so far) and calls `ToolCore.call(target, args, scope)` or `.resume(pinned, scope)`.

```
caller ─> ToolCore.call(spec | (ext, name) | name, args, scope)
   1 spec from the registry (never the caller's or the model's)
   2 args: JSON schema (model-chosen calls) ─> Intent.for_tool (origin; never "explicit" here)
   3 side-effect cap (5 changes that run without asking per task; BA-1, was 3)
   4 gate.evaluate (levels, trust rules, standing allows, principals, kill switch, dry run)
       read, not asked ─> executor ─> Ran | Failed | Refused   (ungated)
   5 pin checkpoint.call (+ effects, taint) before anything runs or is asked;
     batch mode (BA-1): an asked call joins checkpoint.batch instead (≤ gate.batch_max)
   6 Asked (caller prompts, defers, or adds it to its batch) | executor (pinned key) ─> Ran(report line) | Failed
ToolCore.resume(pinned, scope): executions first ─> gate with the pinned origin ─> 6
```

**Batch approvals (BA-1).** A Claude brain turn and a one-shot ask with tools don't stop at the first change that needs approval: each asked call is pinned in the task's `checkpoint.batch` and the model is told `asked the owner: <summary>` (never a code), and it goes on. When the turn ends the owner gets **one** prompt for all of them (`[D7] OK to make these 4 changes?` then a numbered code-built line each, `Reply yes / no, or yes 1,3 D7 for just those.`; with an L1 among them `yes D7` is needed, the batch takes its strictest level, and `yes 1,3` takes the strictest of the picked ones, PER-255). `yes` runs each once, in order, through `ToolCore.resume` (the executor's keys: a restart mid-batch never runs one twice), one failure doesn't stop the rest, and the reply has a line per change; `no` and expiry drop them all, `yes 1,3` drops the others; the kill switch's pause blocks them. The gate stores the batch (`approval_batches`) and binds a reply to it as one unit: only its code names it, only the owner can answer it. A single asked change keeps the plain prompt (and its `yes always`). Contracts: [`interfaces.md`](interfaces.md#approvals-binding-codes-and-replies).

The outcome (`Ran`, `Asked`, `Refused`, `Failed`) carries code-built text only; each caller turns it into its own reply (a templated answer, a tool turn for the model, an MCP result for Claude, a job report). `gate/`, `trust/` and `executor.py` stay their own modules under it. `tests/test_toolcore_boundary.py` scans the package's AST so that no other module calls `gate.evaluate`, `gate.consume`, `Executor.execute` or `Executor.recorded`: a new caller can't skip the gate. There are no exceptions: the scheduler's inline L0 jobs are gated through `ToolCore.call` (origin `scheduled`) over an `InlineExecutor` that only spends the token, then run by the scheduler with no `executions` row (PER-247). Contracts: [`interfaces.md`](interfaces.md#tool-core-resonanttoolcore-tc-1).

## Trust model

- **Identity grants permissions. Content never does.** Every message, email, web page and tool output is untrusted input.
- **Principals.** `principals.yaml` maps channel identities to people. Exactly one owner can do everything, including admin (`/update`, `/ext`, secrets, editing principals, the kill switch's fan-out). PER-293 adds two roles' worth of team: an **approver** (`role: approver`) may request and approve every builtin and every extension but never admin, and may pause and resume only its own instance (`paused_by = approver:<name>`, never a `sibling:resonant` pause); **members** have explicit grants, per extension (`[request, approve]`) or per tool (`{request: [file_ticket]}`). An optional workspace **default** (`default: {channel: slack, grants}`) makes any unlisted Slack user the adapter vouches for a member with those grants; it is never an approver, and iMessage never gets one. On such a team config, a member with any extension grant reaches Claude with only the tools they may request. The co-founder is limited to DORI and can't reach the personal lane, trading, the owner's data, or global settings.
- **Permission is checked before anything else.** A principal without `request` on an extension is denied before any level logic runs. Toolsets are filtered by principal before the model sees them, so a prompt injection can't reach tools the requester lacks.
- **Effects come from registration** (`ToolSpec` or the manifest), never from the model.
  - `pay` is always L1.
  - A read with no secrets is always L0. A write with no declared level is L2 (GT-1; was L1): it runs when the owner asks for it by slash command and asks a plain yes when the model chose it.
  - MCP tools must be typed in the manifest, and unlisted ones are never exposed. Each listed tool is pinned at `ext add` (pin v2, GT-1: `sha256(name, stripped input_schema, stripped output_schema)`, what the model sees and arguments are validated against; a reworded description or new annotations isn't a change) and re-checked at every server start and `list_changed`; a change disables the tool and alerts once (MCP-1, stdio; [`extensions.md`](extensions.md) §4). A v1 pin whose stored input schema still matches is re-pinned once on first start (audited `ext.mcp_pin_migrated`).
- **The gate weighs risk against who chose the action** (Phase 2). The level comes from registration; the origin is `explicit` only for a slash command the router parsed (the local runner's `direct_call` path), `inferred` for anything the model chose, and `scheduled` for a job that fired on its schedule (Phase 3). `scheduled` is never explicit: L0 runs silently, L3 runs and reports to the approvers, L2 asks, L1 asks with a code. `tainted` (BR-5, docs/brain-plan.md D6) is a model-chosen call in a task that has read untrusted content (files, logs, transcripts, the web, email, extension results, `ask_claude` output): L0 reads still run, but L2 **and L3** ask and no standing allow applies, and the prompt is code-built as always, so injected text can neither act unasked nor reword what the owner approves. The exception (PER-245, the owner's call): notes, reminders and facts (`taint_exempt` specs) run on their level even when tainted, and a turn stays tainted only `brain.taint_hops` (3) turns after the outside text. The brain loop (BR-1) tracks taint and sets it. Claude's calls to Resonant's tools (BR-10) are model-chosen too: `inferred`, or `tainted` once its session started tainted or used a tool of its own (Read, the web), and they go through the same gate. A builtin's approvers are the owner plus every approver (PER-293); an extension's are those plus the principals its manifest names that hold `approve` for it (for that tool, under a per-tool grant) in `principals.yaml`; self-approval is allowed, and prompts go to every reachable approver.

  | Level | Explicit (slash command) | Inferred (model) | Kill switch on |
  |---|---|---|---|
  | L0 read | Silent | Silent | Silent |
  | L3 small, reversible | Run, then report | Run, then report | Ask (plain `yes`) |
  | L2 medium | Run, then report | Ask (plain `yes`) | Ask (plain `yes`) |
  | L1 destructive or pay | Ask, `yes <code>` only | Ask, `yes <code>` only | Ask, `yes <code>` only |

  **Standing allows (GT-1).** The first time the model picks an L2 tool for the owner it asks, and the prompt also offers `yes always` (`… (yes always = don't ask before running github.merge_pr in jhe/dori). Reply yes / yes always / no`). The owner's `yes always` saves an `allow` trust rule for that tool on its natural scope (the repo it acts on, else its extension, else everywhere); after that the owner's chat calls of that tool run as L3, do and report. Never for members (their calls ask, and only the owner's reply can save the rule), never for L1 or pay, never for `scheduled` jobs, never for the trust-loosening tools or `merge_run`, and never past the kill switch or dry run. The slash-only control commands aren't model tools, so nothing changes them. The rule is made only by the owner's own reply (or `/rules allow`), never from extension output; `/rules` lists it and `/rules forget <n>` removes it.

  **Tainted writes (PER-335).** A team instance can be self-sufficient: with `gate.tainted_writes: allow` in its own config (default `ask`: nothing changes), the owner's and an approver's tainted L2/L3 writes (any extension's, and of the builtins only the run tools on an allowlist) run as an untainted L3 would (do, post the status line, report), so a ticket or Slack thread the brain read no longer makes every `start_run` or staging deploy ask. PER-348: the same staff L2 writes also run when untainted (a fresh "merge #159" from an approver, who has no standing allows), audited `staff_allowed: true`; `cancel_watch` lifts either way and `create_watch` only untainted. L1 and pay still ask with the code; so do a member's calls, the admin and trust builtins, jobs and a tainted `create_watch` (a stored prompt would later fire untainted), CI workflows and the repo set, anything an `ask` trust rule covers, everything under the kill switch, and a `merge_run` that isn't `merge_standable` (flagged paths, not push mode, an `ask merge` rule). A lifted merge is unattended: green CI and CLEAN, or it doesn't merge. Audited `gate.evaluate` with `tainted_allowed: true`. The trade-off: outside text could steer the instance into an L2/L3 write, never an L1 one. Personal Resonant keeps `ask`; `config/cori.example.yaml` shows `allow`.

  There are no veto windows yet: unattended L2 and L1 jobs ask, and asking jobs may fire at most hourly. `Veto` stays in the contract ([`extensions.md`](extensions.md#veto-windows-for-unattended-jobs)). Under `dry_run`, only the store-internal builtins (notes, reminders) run; everything else that isn't an L0 read replies `Dry run: would …`.
- **Approvals are text replies on iMessage**, bound to a 2-character code and an intent hash. They expire (`gate.approval_ttl_s`, 30 min) and are single use.
  - A deterministic parser reads the whole message (`yes`, `no`, `yes A7`, `A7 no`, `yes A7 with comments: …`, `yes always`). There is no classifier and no `yes all`; a task's several changes come as one batch prompt with one code (BA-1, Tool core above).
  - A plain `yes` binds only when exactly one approval is pending, and only to a prompt sent before the reply. Each chat.db event resolves at most once. With one approval and one worker question open it binds neither and asks which, unless the question offers options none of which is a yes or a no, so it can't take a `yes` (then the approval gets it, GT-1), and the approval isn't a worker's check (a worker writes its own options).
  - L1 (including pay) needs an exact `yes <code>`.
  - Slash commands are checked first, so `/kill` is never read as a reply.
  - SMS-delivered messages are ignored.
  - Summaries are built by code from the registry and the args: sanitized, clipped, with losses marked. `/approvals <code>` shows the full args.
- **Up to five side effects per task without asking, one batch of approvals, and a residual risk.** Within one task, a tool read's output (untrusted) can still steer the model's choice of a write that runs without asking (L3, or an L2 tool the owner gave a standing allow). GT-1 raised the cap from one to 3 and BA-1 to 5 (so "close these 4 Linear tickets" fits under a standing rule): up to 5 such side effects per task, each idempotent on its own; past it a change is refused. Changes that need approval don't count against it: since BA-1 they wait in the task's batch (at most `gate.batch_max`, 10) and the owner answers them once, seeing each one. A task that read outside content is tainted, so its L2 and L3 changes all go into the batch (never run silently), except notes, reminders and facts (PER-245). So one injected read buys at most five effects the owner already lets run unasked. Mitigations: toolsets are owner-only and filtered by intent; the runner prompt treats tool output as data; standing allows are per tool and scope and only the owner's own reply makes one. L2 without a standing allow and L1 always ask when the model chose them.
- **The model never sees secrets.** The executor (and the scheduler, for L0 jobs) reads a tool's or job's declared secrets from the Keychain just before the call and delivers them to that process on an inherited pipe (fd 4), never in its environment or argv, because a same-user process's env and argv are readable (`sysctl KERN_PROCARGS2`) and a sandbox can't deny that. Every encoding of a value (raw, URL, JSON-escaped, base64 at three alignments) is redacted before anything is stored, logged or replied. Secrets are entered only in the Mini's terminal (`resonant secret set`), never over iMessage.
- **Phase 3 extensions: an interim trust bar.** Extensions are first-party, owner-installed code (this repo or a local git work tree), installed only from the Mini's terminal. They run as the same macOS user and inherit the daemon's Full Disk Access, so they can read `resonant.db`, chat.db, other extensions' data and the Keychain like any same-user process. Phase 3's protections are env and secret isolation, not filesystem isolation:
  - an environment built from scratch, with `HOME` and `TMPDIR` in the extension's data dir;
  - per-tool secret injection and redaction;
  - output caps, and a process-group plus tracked-tree kill;
  - an argv[0] allowlist (a `.py` file in the extension, `python3`, `gh`, `git`), stdlib only, Python under `-I -S`;
  - a pinned, copied, read-only tree, re-verified at every start.

  **Keychain ACL residual.** Items are created by `/usr/bin/security` and trust it, so any same-user caller can read every `resonant/*` item, including the owner's own Claude Code sessions and any extension. Accepted for now; tokens are scoped minimally (the github PAT is read-only unless the owner wants the writes). No third-party sources until the Seatbelt sandbox lands ([`extensions.md`](extensions.md#seatbelt-sandbox-for-extension-processes)).
- **Trust rules for workers (EM-4, [`employee-plan.md`](employee-plan.md#d4-trust-rules-standing-trust-net-new-asks-taught-over-chat)).** A Claude worker acts on standing trust and asks only for something net new. Before such an action it checks (`resonant check`, EM-3), and `trust.evaluate` decides: the most specific `allow`/`ask` rule wins (scope before action: the system exactly, then the run's repo or an area like `trading`, then `*`; `ask` beats `allow` on a tie); with no rule, it asks for a new system, a new kind of action on a system, anything irreversible and anything that costs more than `trust.cost_ask_over_usd` (default $20, GT-1; at or under it, cost alone isn't net new). An `ask` becomes an owner approval through the normal approval store, codes and prompts: plain `yes` (L2-style, never a code), with `yes always` offered unless the owner's own `ask` rule made it ask. `yes always` also adds `allow <action>` on that system. The parser reads `yes always` only as that: the gate refuses it for every approval that didn't offer it (`always_unsupported`; the offers are a worker's check and an owner's L2 chat tool call, GT-1), so it can't stand in for `yes <code>` on an L1 or pay prompt or for a plain yes elsewhere, and only the owner's `yes always` makes a rule (a worker can't text; PER-318: only the owner's prompt offers it, and an approver's `yes always` is a plain yes, `Approved this once. Only <Owner> can make it standing.`). The prompt always names the action and system the rule would cover and quotes the worker's own words; `yes always` isn't offered when the system is an area of other known systems. Chat-taught rules that tighten trust or raise urgency (`add_trust_rule`) run and report `Rule added: …`; anything that loosens trust or lowers urgency from chat (`allow_trust_rule`, `remove_trust_rule` by number, and since BA-1 `allow_tools`: "don't ask for Linear tickets" saves the standing allows of the extension's L2 changes, its prompt naming exactly which tools stop asking) is L2, so a model-chosen call asks the owner a plain yes with a code-built prompt. Every check, rule change and merge decision is audited (`trust.*`). This is honor-system by design: the worker is trusted to call `check`. With `runner.guard: thin` the thin guard (D2) is the hard floor; with the default `off` there is no floor (below).
- **trade-jev order execution never goes through the loop or gate.** Core only sees its jobs, read tools, events and kill switch.
- **The kill switch** sets `autonomy=off`, so everything above L0 asks first (L1 still needs its code), and `paused=true`: due jobs are skipped and never caught up, in-flight extension processes are killed, and notifications and the briefing are held (not sent later). A missing or garbage `autonomy` counts as off.
- **Fork mode and merges (EM-7, [`employee-plan.md`](employee-plan.md#em-7-fork-mode-as-a-worker-merge-per-trust-rules)).** Three GitHub credentials stay apart: the daemon's token (mirror, reads, merges), the App's per-run installation token (one repo: the push repo, or for a fork run the owner's fork, so a fork session can't open or touch anything upstream) and the optional `public_repo` token (only forking and opening or closing an upstream PR, from the daemon, never in env, argv or a session). No upstream PR is opened without the owner's ok on an `external_pr` check showing that change, and the PR must sit at the checked head or it is closed. Every merge, `/merge`, chat or auto, goes through `Workspace.merge` and its pre-merge checks, CI and `--match-head-commit`; fork repos are never merged. Flagged paths (GT-1) are only what runs in CI or local tooling without review: `.github/`, `.claude/`, `.mcp.json`, git hooks (`.githooks/`, `.husky/`, pre-commit and lefthook config), `CODEOWNERS`, other CI config (`.gitlab-ci.yml`, `.circleci/`, `Jenkinsfile`, …), package-manager config that runs code on install (`.npmrc`, `.yarnrc*`) and what runs on open (`.envrc`, `.devcontainer`, `.vscode/tasks.json`); they stop an auto-merge and make a chat merge ask. Dependency manifests and lockfiles merge and are listed in the merged report (`deps changed: uv.lock`). An owner's `/merge` (or a yes'd chat merge) while CI is pending waits for it, bounded like the auto-merge, and reports; in a repo with no CI it merges with a warning (`merged without CI`); red CI still refuses. The auto-merge never merges without CI, and a model-chosen merge in a repo whose CI isn't known to exist always asks.
- **Local code is outside the gate's threat model.** The gate protects against remote principals, iMessage content and the model, not against processes running as the same macOS user: those can run `resonant approvals approve` or `resonant resume`, write `~/.resonant/resonant.db`, and read the Keychain. Phase 3 extension processes are such processes (see the interim bar above) and are not yet sandboxed ([`extensions.md`](extensions.md#seatbelt-sandbox-for-extension-processes)). **Claude workers with the guard off (the default since GD-1) are such processes too.** A worker runs as the owner with the real `HOME` and no sandbox: it could in principle read the Keychain (every `resonant/*` item, the GitHub App key), `~/.resonant` (the DB, config, logs, run secrets), Messages, signal the daemon or run `resonant approvals approve`. Trust rules, `resonant check` and approvals are followed by the worker because its prompt says so, not enforced by the OS. The owner accepted this for the dedicated Mini (2026-10-16). What the owner sees: merges, restarts and updates done through Resonant reach the digest (a worker's `resonant restart`/`update` texts right away unless a rule holds it), and the worker is told to `resonant note "did: …"` any side effect it takes outside Resonant's tools (a merge with `gh`, a deploy, a push to another repo, an email, a payment), which its final digest line lists (GT-1). That is also honor-system, so Resonant also reads the worker's own tool calls as they stream (TR-1): pushes to the base branch or another repo, `gh pr merge`, releases, deploys, publishes, HTTP writes (method and host only), emails and messages, and writing MCP tools land on the same `did:` line marked `(detected)`, and the high-impact ones (base push, a `gh pr merge` the worker ran itself, publish, delete) text right away. It reads command text only, so it can miss what a script or a tool does inside, and it says what was run, not whether it worked. What still holds: no Resonant secret is in a worker's env or argv except its own Claude credential (none when it uses the owner's login), the per-run GitHub token covers one repo for an hour, every merge Resonant performs goes through its pre-merge checks, the reaper and `/kill` end every run, and transcripts are redacted. **With `runner.guard: thin`,** each session and its children run under the **thin guard** ([`employee-plan.md`](employee-plan.md#d2-thin-guard-sandbox-replaces-the-phase-5a-profile), EM-1), an allow-default Seatbelt profile. A worker reads, writes, connects and runs like the owner at the keyboard (`.env` files, Docker, the network, the whole disk), except that it can't:
  - write the following, nor rename any ancestor dir of them (a `literal` deny on each, since a `subpath` rule follows the path, not the files), nor mount a disk image over any of them:
    - `~/.resonant` (DB, config, logs) or `$RESONANT_HOME`;
    - the installed daemon: its venv, the interpreter it runs on, its checkout and the `resonant` entry point;
    - the `gh`, `uv`, `ollama` and `git` it runs outside the guard by absolute path, with their Homebrew kegs (the PATH dirs themselves stay open for `brew install` and `uv tool install`: the daemon runs with a system-only PATH and never looks a tool up by name);
    - the real target of any symlinked path in the profile;
  - read or write `runner.secrets_dir` (`~/.resonant/run-secrets`), `~/Library/Messages`, the Keychain files or any `runner.deny_read` path;
  - look up securityd (`com.apple.SecurityServer`, `com.apple.securityd*` and its agents; `trustd` stays, so TLS works), launchd, the Messages agents, Apple Events, LaunchServices, the window server, HID or accessibility; send Apple Events or open apps; open the HID drivers;
  - write auto-start entries: `~/Library` (LaunchAgents, login items), `~/.config`, `~/.claude`, `~/.ssh`, the shell and git startup files, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, the login-item store, the cron and at spools; or exec `launchctl`, `crontab`, `at` or the daemon's venv;
  - signal or take the task port of any process outside its own sandbox (the daemon, the kill switch), or reach port 7777 on any address.

  Hardlinking, renaming out, writing through a symlink and the `/.vol/<dev>/<inode>` path are all refused by the same rules (checked in the EM-1 spike). `resonant sandbox check` proves every deny and every owner-like allow after each OS update, and a self-probe (a write into `~/.resonant`, a securityd lookup, port 7777) fails closed before each run. Residual: a sandboxed process can read another same-user process's argv and environment, so no Resonant secret is put in one except the session's own Claude token; a run's GitHub token reaches the session through its credential-helper files, and repo keys through the checkout's `.env`.

## Health

- **Watchdog.** An asyncio heartbeat beats every second, and a separate thread calls `os._exit(1)` if it goes stale. launchd then restarts the daemon.
- **Dead-man switch.** The status relay ([`dashboard-plan.md`](dashboard-plan.md) D6, go-live step 15). While `relay.enabled`, the daemon pushes a `remote` snapshot to Supabase every minute, and the checker on Fly alerts the owner's phone (ntfy or a webhook, never through the Mini) when none has arrived for 5 minutes, when a snapshot reports a `failing` row, or when it can't read Supabase, and once more on each recovery. Since PER-305 it watches each instance in `RELAY_INSTANCES` on its own (Cori stale while personal is fresh is one Cori alert), and an instance's alerts can also go to its own Slack Incoming Webhook (`SLACK_WEBHOOK_CORI` posts to `#voyager-pulse`); personal stays on ntfy with unchanged text. Presence is the other half (PER-303): with `pulse.heartbeat.room` set, Cori posts a one-line `✓ Cori up · …` (or `⏸ Cori paused · …`) to `#voyager-pulse` every hour from `core/pulse`, so a gap in the room plus the checker's alert tell the same story from both sides. A whole-process freeze (SIGSTOP), a power cut, or a reboot waiting at the FileVault login all stop the snapshots. The older ping still works on its own: with `health.healthchecks_url` set, the daemon GETs it while the loop is ticking and POSTs `<url>/fail` with the reason when it isn't. `--check`'s advisory `dead-man switch` row passes with either.
- **Store backups (BK-1).** Every day at `backup.daily_at` (03:30 local) `core/backup` copies `resonant.db` with SQLite's online backup API (safe while the daemon writes; a `cp` of a WAL database isn't), checks the copy with `PRAGMA integrity_check` and only then renames it into `~/.resonant/backups/daily/`. A failed copy keeps every older one. The newest 7 copies and the newest 4 Sunday copies are kept; nothing else under `backups/` is ever deleted. With no good copy for 36h the `backup` check degrades and the owner gets one alert; success is silent. It runs while paused (below). Restore is `resonant backup restore <file>` with the daemon stopped (go-live, "Restoring the store").
- **Secret expiry (PER-313).** Each instance watches its own Keychain service. An expiry is metadata in the store (`secret_expiry`, migration 035) or an assumed default from the Keychain item's `mdat` attribute (`security find-generic-password` without `-w`); a value is never read for it. `core/secrets` (10:00 local, not while paused, catch-up 20h) tells the owner once per threshold (30, 7, 1 days, expired), only the tightest reached, and a renewal (a new `expires_at`) re-arms it. The health monitor's `secrets` row shows it (`failing` once expired) but never alerts: the job owns that, so the owner hears it once. With no rows and no known secret present nothing changes. PER-315: the snapshot lists the watched expiries (`secrets`, soonest 16, the same Keychain facts the health row caches, so a dashboard poll adds no Keychain call within the hour), `relay_status` carries each instance's soonest 5 and the page shows a Credentials card, both instances side by side; names and dates only, never a value.
- **Credential probes (PER-314).** The same daily job then asks each credential's API whether it still works: one read-only call per probe-able ref the Keychain holds (`resonant/secret_probes.py` has the table), the value in one request header and nowhere else. Core jobs get no secrets through the job runner, so, like the pusher and `OwnerBridge`, the probe reads the instance's `SecretStore` itself. A `rejected` credential (401, or a 403 that isn't a rate limit) is told at once, once per incident, on the expiry alert paths and makes the `secrets` row `failing`; a timeout, 5xx or rate limit is `unknown` and silent, so a machine offline for days never alerts. An API that reports its expiry (GitHub fine-grained tokens, Vercel) fills the `secret_expiry` row as `probe`, which an `owner` row overrides only when sooner. `runner/claude_token` is not probed: there is no quota-free server check. Refs already checked all the time (the relay key, Slack's tokens, the notify token) aren't probed again. Nothing probe-able present: no request.
- **iMessage self-test (Phase 1).** The health monitor runs it on its first round after start whenever it is due (none yet, older than 6h, or a failure older than 30 min) and re-runs it every 6h; a failure (AppleScript or the `chat.db` schema broke) degrades the `imessage` check. It sends a random nonce to Resonant's own handle and waits for the reader to see it; the result is kept in kv `imessage.selftest`. `resonant selftest imessage` runs the same check by hand, next to a live daemon.
- **Health monitor (Phase 1).** `resonant/monitor.py` evaluates `model`, `imessage`, `loop`, `store` and `backup` (BK-1) every 60s, keeps an `ok → degraded → ok` state per check in kv `health.<check>`, and texts the owner through the channel hub ("hey, some issues here: …", then "resolved: …"), at most once per check per 6h. PER-292: each enabled channel has its check (`imessage` keeps its name and kv `health.imessage`; another adapter's is `health.<name>`: not started, a reader error, or a failed self-test), and the hub sends the alert over the owner's first running identity. When every channel check is degraded (iMessage-only: iMessage itself), nothing is sent, and the dead-man `/fail` ping carries the reason as a plain-text body instead. State shows in `/api/status.health`, `GET /api/channels` and `resonant status`.
