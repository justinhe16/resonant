# Resonant architecture

Resonant is an always-on personal agent harness that runs as a daemon on a dedicated home Mac mini. It takes events in from iMessage, Slack, webhooks, schedules and extensions. A local LLM (the **brain**) reads every message, answers what it can and routes the rest to tools. Engineering and ops work goes to **Claude workers** it spawns, which run like the owner at the keyboard, by default with no sandbox (`runner.guard: off`; a **thin guard** that protects only Resonant is the `thin` option) ([`employee-plan.md`](employee-plan.md)). Every side effect of Resonant's own tools passes a policy gate; workers act on standing trust and ask only for something net new. Product logic lives in **extensions**, which are separate repos that plug in through `resonant.yaml`.

For an interactive version, open [`architecture.html`](architecture.html), which has a clickable graph, the lifecycle, the approval flow, the roadmap and the trust model. The frozen contracts are in [`interfaces.md`](interfaces.md).

## Shape

```
 iMessage (owner) ─────┐ principal map   ┌── runner=local : router (fast path · approvals · relay)
 Slack (owner+cofndr) ─┤ (identity →     │                  → brain: qwen3 (≤3 tool calls)
 Webhook (HMAC, TBD) ──┼─> principal) ─> events ─> Loop ─┤── runner=claude: Claude workers (≤4), each in a
 Scheduler / ext emit ─┤                 (event+tick)     │     worktree of ~/code/<repo> or a scratch dir,
 Worker events ────────┘                                  │     guard off by default; resonant ask/note/check
                                                          │     over a per-run socket → worker desk
                                                          └── runner=cu    : computer use (Phase 7)
   worker desk ── ask ──> relay ──> owner "R4 asks: …" ──> reply routed back to R4
               ── check ─> trust rules (ok | ask: yes / yes always / no)
   run events ──> reports: now (text) | digest (hourly pulse "Workers:")
                       Permissions(principal, extension) → Gate(level, scope, approvers) → Executor
                         (idempotency key, Keychain secrets, audit: requested_by / approved_by)
   Store (SQLite WAL): tasks · events · approvals · runs · run_questions · trust_rules · repos · pulse_items · audit_log · kv
   FastAPI on 127.0.0.1 (loopback only)     │   watchdog thread + dead-man ping   │   LaunchAgents
```

- **One asyncio process** runs the loop and the local API. Extensions, MCP servers, Claude workers and computer-use workers run as child processes, so a crash never takes down the core.
- **launchd supervises it** as a per-user LaunchAgent (`gui/<uid>`). Messages.app, computer use and the login Keychain all need the GUI session. Ollama has its own LaunchAgent (`OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_CONTEXT_LENGTH=32768`). Extension jobs run on the daemon's scheduler. Critical jobs with their own LaunchAgents (through `resonant job-guard`, which honors the kill switch) are deferred ([`followups.md`](followups.md#critical-job-launchagents-and-job-guard)).
- **There are no public ports.** The API binds to loopback only, and config validation enforces it. iMessage reads `chat.db` locally. Slack uses Socket Mode. Inbound webhooks have no transport yet: with no tailnet, how third parties reach `/hooks` without a public port is an open follow-up (see [`followups.md`](followups.md#inbound-webhooks)). They must still be HMAC-signed. CI status is polled, never pushed to us. Remote status goes through a push-only, read-only status relay (the Mini pushes to Supabase; a Fly app serves the dashboard and the dead-man checker), so this rule stays: see [`dashboard-plan.md`](dashboard-plan.md) and go-live step 15.
- **Runtime state** lives in `~/.resonant/`: `config.yaml`, `principals.yaml`, `resonant.db`, `logs/`, `evals/`, `extensions/` (approved read-only copies), `ext-data/` (each extension's writable state), `runner/` (daemon-only mirrors, transcripts) and `run-secrets/`. Workers write elsewhere: the owner's checkouts and their worktrees and scratch dirs in `~/code` (`runner.code_dir`), and run dirs (the session's tmp and credentials, and its home under `runner.guard: thin`) in `~/resonant-runs` (`runner.work_dir`). With the guard off (the default) a worker's `HOME` is the owner's.

## Employee mode

The owner texts Resonant like an employee ([`employee-plan.md`](employee-plan.md); it replaced the remaining waves of [`repos-plan.md`](repos-plan.md) and the strict sandbox of [`phase5a-plan.md`](phase5a-plan.md), both now historical).

| Part | What it does | Where |
|---|---|---|
| Brain | The local model routes every message. Work for Claude becomes `start_run` (plain words or `/run [<repo>] <ask>`), acked at once: `On it: R4 · dori.` | `resonant/router/`, `resonant/tools/runs.py` |
| Workers | A Claude Code session per run, up to 4 at once. It works in a git worktree of the owner's real checkout (`~/code/<repo>`, cloned on first use, `.env` files linked in), or in a scratch dir for an ask with no repo. It pushes, opens the PR and watches CI with a per-run GitHub App token (one repo, one hour, no Administration). Only the Claude credential is required: until the App and the daemon's token are set up, a repo run commits to its local branch and says it can't push yet (RX-1). | `resonant/runners/claude.py`, `resonant/runner/workspace.py`, `resonant/runner/github_app.py` |
| Guard | Off by default (`runner.guard: off`, GD-1): a worker runs like the owner at the keyboard, with the real `HOME` and the owner's Claude setup (`~/.claude` skills, `CLAUDE.md`, settings, MCP servers, and the stored `claude` login when no token is set). `thin` puts an allow-default Seatbelt profile around every worker that protects only Resonant: its state and daemon, run secrets, iMessage, the Keychain, auto-start entries, signals to the daemon, the API port. | `resonant/sandbox/`, `resonant/runner/claude_auth.py` |
| Worker CLI and desk | `resonant ask`, `note`, `check`, `restart` and `update` on the session's PATH, over a per-run socket. A question unanswered when the turn ends parks the run (`waiting(question)`, slot freed) until the answer resumes the same session. `restart`/`update` run the `/restart resonant` and `/update` ops (allowed when the owner's ask mentions it, else a trust check); the run resumes after the restart. The daemon's own checkout is the repo `resonant`, so workers can fix Resonant in a worktree. | `resonant/runners/worker_cli.py`, `worker_desk.py` |
| Relay | Texts `R4 asks: …` and routes the owner's reply to the right worker: by code, by option, by content (echoed `→ R4 (<q>)`) or after `For R4 or R6?`. `tell R4 …` reaches a running worker. | `resonant/router/relay.py`, `resonant/worker_text.py` |
| Live sessions and Remote Control | Each worker runs with stream-json input and stdin open (RC-1): `tell R4 …` and an answer that comes after `resonant ask` gave up are written into the running session, and Resonant ends the session once a turn ends with nothing more to send (park and `--resume` stay for news that comes later). With `runner.remote_control: on` (the default) each session opens a Remote Control session, through an undocumented control request; the owner gets its link once (`R4 Remote Control: https://claude.ai/code/…`), also in `/runs R4`, "what's R4 doing" and the local dashboard, never the relay. | `resonant/runners/live.py`, `resonant/runners/claude.py` |
| Trust rules | Standing trust: a worker checks before anything net new (a new system or kind of action, irreversible, over `trust.cost_ask_over_usd`) and gets `ok` or an owner ask (`yes` / `yes always` / `no`). Rules are taught over chat ("always ask before merging in trading") or `/rules allow`; merges follow them. The owner's L2 chat tools take `yes always` too (standing allows, GT-1). | `resonant/trust/`, `resonant/store/trust.py`, `resonant/tools/trust.py` |
| Reports and digest | Failures, questions, checks, urgent notes and a worker's `resonant restart`/`update` text now. PRs, done and merged (with `deps changed: …`) go to the hourly pulse's `Workers:` section, one line per run, told exactly once, with a `did:` list of the side effects the worker noted (GT-1) and those Resonant read in its commands, marked `(detected)` (TR-1); a detected push to the base branch, publish or delete texts now. `run_activity` ("what's R4 doing", `/runs R4`) reads the transcript tail. | `resonant/runners/reports.py`, `resonant/runners/side_effects.py`, `resonant/runners/activity.py`, `resonant/extensions/pulse_job.py` |
| Repos | A registry the owner shapes over chat (`/repos`, `/repo add`, "create a repo"); fork mode for others' public repos, with the upstream PR opened by the daemon after an `external_pr` check. | `resonant/store/repos.py`, `resonant/runner/resolve.py`, `resonant/tools/repos.py` |

`tests/test_e2e_employee.py` runs the plan's exit criteria end to end through the real daemon: a spawn to a PR in the digest, three workers asking at once, the guard under the real `sandbox-exec`, `yes always`, a rule taught over chat, and a scratch run.

## Phase 1 request path and latency

```
chat.db row ─(WAL watch 250ms + 100ms debounce; 2s poll fallback)─> IMessageReader ─> loop.submit
  ─> Router.route: fast path (one gated builtin read, templated reply)  │ or one LLM label call
  ─> NewTask(runner="local") ─> LocalRunner: send fast_reply │ ≤3 tool calls (gate → executor) + answer
  ─> IMessageChannel.send (dedupe "reply:<task id>") ─> osascript
```

The Phase 1 exit criterion is **text → answer in 2–3s**: p50 ≤ 1s on the fast path and p50 ≤ 3s on the labeled path, measured by `resonant bench e2e` from the chat.db row insert to the osascript call (Messages.app delivery and osascript's own run time excluded; the self-test covers that path).

| Run | Model | fast p50 / p95 | llm p50 / p95 |
|---|---|---|---|
| Dev machine, `--model fake` (n=20; CI runs the same code) | scripted | 354 / 370 ms | 354 / 361 ms |
| Mac mini (Apple M5 Pro, 64 GB), macOS 27.0.1, Ollama 0.40.3, `--model real` (n=20, 2026-10-13) | `qwen3:30b-a3b-instruct-2507-q4_K_M` (Ollama) | 353 / 367 ms | 1531 / 2129 ms |
| Same Mini, after Phase 3.5 (n=20, 2026-10-14) | same | 354 / 366 ms | 1384 / 2335 ms |

`resonant model bench` on the same run: label p50 / p95 86 / 89 ms, single tool call 229 / 232 ms, 0/20 failures.

With the scripted model nearly all of the time is the reader's WAL-watch interval plus its debounce, so the harness overhead is about 0.35s; on the Mini the labeled path adds the label call, up to three tool rounds, and the answer call.

## Task lifecycle

```
queued ──dispatch──> running ──Continue──> queued
                        │──Wait(reason, wake_at?)──> waiting ──event or wake_at──> queued
                        │──Done──> done
                        │──Fail(retryable, attempts left)──> queued (backoff or retry_at; events kept)
                        └──Fail(final) / cancel ──> failed / cancelled
wait reasons: approval · human_reply (also a worker question: run wait_reason=question) · usage_reset · ci · veto (reserved; veto windows are deferred)
```

- One transaction per step commits the outcome, the checkpoint and the consumed events together.
- A crash mid-step leaves the task `running` with its last checkpoint and its events unconsumed. On the next start it is requeued, and the crash counts as an attempt, so crash loops are bounded. A graceful shutdown requeues without using an attempt.
- Runners save anything a retry must not lose with `ctx.save(...)`. For example, `claude_session_id` is saved as soon as the session starts.
- Side effects are idempotent through `executions`. A key that succeeded is never re-run. A key that started but never finished is reported as ambiguous instead of being retried blindly.

## Scheduling and priority

- Priority is set by lane and principal, never by the model: **on-call 0 < owner 1 < co-founder 2 < background 3**.
- At most `max_parallel` steps run at once, and the last parallel slot is kept for on-call.
- Claude sessions also need a slot from `SlotPool`. The cap defaults to 5, with 1 slot reserved for on-call.
- A slot is held only while a step is in flight. A session that needs to wait (approval, human reply, usage reset, CI) returns `Wait`, which frees the slot, and resumes later by `claude_session_id`. Running sessions are never preempted.
- Usage limits are not throttled ahead of time. When a limit is hit, the affected tasks are parked with `wait_reason=usage_reset` and `wake_at`, they resume automatically, and you are notified once.

## Trust model

- **Identity grants permissions. Content never does.** Every message, email, web page and tool output is untrusted input.
- **Principals.** `principals.yaml` maps channel identities to people. Exactly one owner can do everything, including admin (kill switch, global settings). Everyone else has explicit per-extension `request` and `approve` grants. The co-founder is limited to DORI and can't reach the personal lane, trading, the owner's data, or global settings.
- **Permission is checked before anything else.** A principal without `request` on an extension is denied before any level logic runs. Toolsets are filtered by principal before the model sees them, so a prompt injection can't reach tools the requester lacks.
- **Effects come from registration** (`ToolSpec` or the manifest), never from the model.
  - `pay` is always L1.
  - A read with no secrets is always L0. A write with no declared level is L2 (GT-1; was L1): it runs when the owner asks for it by slash command and asks a plain yes when the model chose it.
  - MCP tools must be typed in the manifest, and unlisted ones are never exposed. Each listed tool is pinned at `ext add` (pin v2, GT-1: `sha256(name, stripped input_schema, stripped output_schema)`, what the model sees and arguments are validated against; a reworded description or new annotations isn't a change) and re-checked at every server start and `list_changed`; a change disables the tool and alerts once (MCP-1, stdio; [`extensions.md`](extensions.md) §4). A v1 pin whose stored input schema still matches is re-pinned once on first start (audited `ext.mcp_pin_migrated`).
- **The gate weighs risk against who chose the action** (Phase 2). The level comes from registration; the origin is `explicit` only for a slash command the router parsed (the local runner's `direct_call` path), `inferred` for anything the model chose, and `scheduled` for a job that fired on its schedule (Phase 3). `scheduled` is never explicit: L0 runs silently, L3 runs and reports to the approvers, L2 asks, L1 asks with a code. An extension's approvers are the owner plus the principals its manifest names that hold `approve` for it in `principals.yaml`; prompts go to every reachable approver.

  | Level | Explicit (slash command) | Inferred (model) | Kill switch on |
  |---|---|---|---|
  | L0 read | Silent | Silent | Silent |
  | L3 small, reversible | Run, then report | Run, then report | Ask (plain `yes`) |
  | L2 medium | Run, then report | Ask (plain `yes`) | Ask (plain `yes`) |
  | L1 destructive or pay | Ask, `yes <code>` only | Ask, `yes <code>` only | Ask, `yes <code>` only |

  **Standing allows (GT-1).** The first time the model picks an L2 tool for the owner it asks, and the prompt also offers `yes always` (`… (yes always = don't ask before running github.merge_pr in jhe/dori). Reply yes / yes always / no`). The owner's `yes always` saves an `allow` trust rule for that tool on its natural scope (the repo it acts on, else its extension, else everywhere); after that the owner's chat calls of that tool run as L3, do and report. Never for members (their calls ask, and only the owner's reply can save the rule), never for L1 or pay, never for `scheduled` jobs, never for the trust-loosening tools or `merge_run`, and never past the kill switch or dry run. The slash-only control commands aren't model tools, so nothing changes them. The rule is made only by the owner's own reply (or `/rules allow`), never from extension output; `/rules` lists it and `/rules forget <n>` removes it.

  There are no veto windows yet: unattended L2 and L1 jobs ask, and asking jobs may fire at most hourly. `Veto` stays in the contract ([`followups.md`](followups.md#veto-windows-for-unattended-jobs)). Under `dry_run`, only the store-internal builtins (notes, reminders) run; everything else that isn't an L0 read replies `Dry run: would …`.
- **Approvals are text replies on iMessage**, bound to a 2-character code and an intent hash. They expire (`gate.approval_ttl_s`, 30 min) and are single use.
  - A deterministic parser reads the whole message (`yes`, `no`, `yes A7`, `A7 no`, `yes A7 with comments: …`, `yes always`). There is no classifier and no `yes all` yet ([`followups.md`](followups.md)).
  - A plain `yes` binds only when exactly one approval is pending, and only to a prompt sent before the reply. Each chat.db event resolves at most once. With one approval and one worker question open it binds neither and asks which, unless the question offers options none of which is a yes or a no, so it can't take a `yes` (then the approval gets it, GT-1), and the approval isn't a worker's check (a worker writes its own options).
  - L1 (including pay) needs an exact `yes <code>`.
  - Slash commands are checked first, so `/kill` is never read as a reply.
  - SMS-delivered messages are ignored.
  - Summaries are built by code from the registry and the args: sanitized, clipped, with losses marked. `/approvals <code>` shows the full args.
- **Up to three side effects per task, one approval, and a residual risk.** Within one task, a tool read's output (untrusted) can still steer the model's choice of a write that runs without asking (L3, or an L2 tool the owner gave a standing allow). GT-1 raised the cap from one: the local runner runs up to 3 such side effects per chat task, each idempotent on its own; anything that needs approval stops the task and asks, one approval per task. So one injected read buys at most three effects the owner already lets run unasked. Mitigations: toolsets are owner-only and filtered by intent; the runner prompt treats tool output as data; standing allows are per tool and scope and only the owner's own reply makes one. L2 without a standing allow and L1 always ask when the model chose them.
- **The model never sees secrets.** The executor (and the scheduler, for L0 jobs) reads a tool's or job's declared secrets from the Keychain just before the call and delivers them to that process on an inherited pipe (fd 4), never in its environment or argv, because a same-user process's env and argv are readable (`sysctl KERN_PROCARGS2`) and a sandbox can't deny that. Every encoding of a value (raw, URL, JSON-escaped, base64 at three alignments) is redacted before anything is stored, logged or replied. Secrets are entered only in the Mini's terminal (`resonant secret set`), never over iMessage.
- **Phase 3 extensions: an interim trust bar.** Extensions are first-party, owner-installed code (this repo or a local git work tree), installed only from the Mini's terminal. They run as the same macOS user and inherit the daemon's Full Disk Access, so they can read `resonant.db`, chat.db, other extensions' data and the Keychain like any same-user process. Phase 3's protections are env and secret isolation, not filesystem isolation:
  - an environment built from scratch, with `HOME` and `TMPDIR` in the extension's data dir;
  - per-tool secret injection and redaction;
  - output caps, and a process-group plus tracked-tree kill;
  - an argv[0] allowlist (a `.py` file in the extension, `python3`, `gh`, `git`), stdlib only, Python under `-I -S`;
  - a pinned, copied, read-only tree, re-verified at every start.

  **Keychain ACL residual.** Items are created by `/usr/bin/security` and trust it, so any same-user caller can read every `resonant/*` item, including the owner's own Claude Code sessions and any extension. Accepted for now; tokens are scoped minimally (the github PAT is read-only unless the owner wants the writes). No third-party sources until the Seatbelt sandbox lands ([`followups.md`](followups.md#seatbelt-sandbox-for-extension-processes)).
- **Trust rules for workers (EM-4, [`employee-plan.md`](employee-plan.md#d4-trust-rules-standing-trust-net-new-asks-taught-over-chat)).** A Claude worker acts on standing trust and asks only for something net new. Before such an action it checks (`resonant check`, EM-3), and `trust.evaluate` decides: the most specific `allow`/`ask` rule wins (scope before action: the system exactly, then the run's repo or an area like `trading`, then `*`; `ask` beats `allow` on a tie); with no rule, it asks for a new system, a new kind of action on a system, anything irreversible and anything that costs more than `trust.cost_ask_over_usd` (default $20, GT-1; at or under it, cost alone isn't net new). An `ask` becomes an owner approval through the normal approval store, codes and prompts: plain `yes` (L2-style, never a code), with `yes always` offered unless the owner's own `ask` rule made it ask. `yes always` also adds `allow <action>` on that system. The parser reads `yes always` only as that: the gate refuses it for every approval that didn't offer it (`always_unsupported`; the offers are a worker's check and an owner's L2 chat tool call, GT-1), so it can't stand in for `yes <code>` on an L1 or pay prompt or for a plain yes elsewhere, and only the owner's iMessage can answer (a worker can't text, and a member's `yes always` is refused). The prompt always names the action and system the rule would cover and quotes the worker's own words; `yes always` isn't offered when the system is an area of other known systems. Chat-taught rules that tighten trust or raise urgency (`add_trust_rule`) run and report `Rule added: …`; anything that loosens trust or lowers urgency from chat (`allow_trust_rule`, `remove_trust_rule` by number) is L2, so a model-chosen call asks the owner a plain yes with a code-built prompt. Every check, rule change and merge decision is audited (`trust.*`). This is honor-system by design: the worker is trusted to call `check`. With `runner.guard: thin` the thin guard (D2) is the hard floor; with the default `off` there is no floor (below).
- **trade-jev order execution never goes through the loop or gate.** Core only sees its jobs, read tools, events and kill switch.
- **The kill switch** sets `autonomy=off`, so everything above L0 asks first (L1 still needs its code), and `paused=true`: due jobs are skipped and never caught up, in-flight extension processes are killed, and notifications and the briefing are held (not sent later). A missing or garbage `autonomy` counts as off.
- **Fork mode and merges (EM-7, [`employee-plan.md`](employee-plan.md#em-7-fork-mode-as-a-worker-merge-per-trust-rules)).** Three GitHub credentials stay apart: the daemon's token (mirror, reads, merges), the App's per-run installation token (one repo: the push repo, or for a fork run the owner's fork, so a fork session can't open or touch anything upstream) and the optional `public_repo` token (only forking and opening or closing an upstream PR, from the daemon, never in env, argv or a session). No upstream PR is opened without the owner's ok on an `external_pr` check showing that change, and the PR must sit at the checked head or it is closed. Every merge, `/merge`, chat or auto, goes through `Workspace.merge` and its pre-merge checks, CI and `--match-head-commit`; fork repos are never merged. Flagged paths (GT-1) are only what runs in CI or local tooling without review: `.github/`, `.claude/`, `.mcp.json`, git hooks (`.githooks/`, `.husky/`, pre-commit and lefthook config), `CODEOWNERS`, other CI config (`.gitlab-ci.yml`, `.circleci/`, `Jenkinsfile`, …), package-manager config that runs code on install (`.npmrc`, `.yarnrc*`) and what runs on open (`.envrc`, `.devcontainer`, `.vscode/tasks.json`); they stop an auto-merge and make a chat merge ask. Dependency manifests and lockfiles merge and are listed in the merged report (`deps changed: uv.lock`). An owner's `/merge` (or a yes'd chat merge) while CI is pending waits for it, bounded like the auto-merge, and reports; in a repo with no CI it merges with a warning (`merged without CI`); red CI still refuses. The auto-merge never merges without CI, and a model-chosen merge in a repo whose CI isn't known to exist always asks.
- **Local code is outside the gate's threat model.** The gate protects against remote principals, iMessage content and the model, not against processes running as the same macOS user: those can run `resonant approvals approve` or `resonant resume`, write `~/.resonant/resonant.db`, and read the Keychain. Phase 3 extension processes are such processes (see the interim bar above) and are not yet sandboxed ([`followups.md`](followups.md#seatbelt-sandbox-for-extension-processes)). **Claude workers with the guard off (the default since GD-1) are such processes too.** A worker runs as the owner with the real `HOME` and no sandbox: it could in principle read the Keychain (every `resonant/*` item, the GitHub App key), `~/.resonant` (the DB, config, logs, run secrets), Messages, signal the daemon or run `resonant approvals approve`. Trust rules, `resonant check` and approvals are followed by the worker because its prompt says so, not enforced by the OS. The owner accepted this for the dedicated Mini (2026-10-16). What the owner sees: merges, restarts and updates done through Resonant reach the digest (a worker's `resonant restart`/`update` texts right away unless a rule holds it), and the worker is told to `resonant note "did: …"` any side effect it takes outside Resonant's tools (a merge with `gh`, a deploy, a push to another repo, an email, a payment), which its final digest line lists (GT-1). That is also honor-system, so Resonant also reads the worker's own tool calls as they stream (TR-1): pushes to the base branch or another repo, `gh pr merge`, releases, deploys, publishes, HTTP writes (method and host only), emails and messages, and writing MCP tools land on the same `did:` line marked `(detected)`, and the high-impact ones (base push, a `gh pr merge` the worker ran itself, publish, delete) text right away. It reads command text only, so it can miss what a script or a tool does inside, and it says what was run, not whether it worked. What still holds: no Resonant secret is in a worker's env or argv except its own Claude credential (none when it uses the owner's login), the per-run GitHub token covers one repo for an hour, every merge Resonant performs goes through its pre-merge checks, the reaper and `/kill` end every run, and transcripts are redacted. **With `runner.guard: thin`,** each session and its children run under the **thin guard** ([`employee-plan.md`](employee-plan.md#d2-thin-guard-sandbox-replaces-the-phase-5a-profile), EM-1), an allow-default Seatbelt profile. A worker reads, writes, connects and runs like the owner at the keyboard (`.env` files, Docker, the network, the whole disk), except that it can't:
  - write the following, nor rename any ancestor dir of them (a `literal` deny on each, since a `subpath` rule follows the path, not the files), nor mount a disk image over any of them:
    - `~/.resonant` (DB, config, logs) or `$RESONANT_HOME`;
    - the installed daemon: its venv, the interpreter it runs on, its checkout and the `resonant` entry point;
    - the `gh`, `uv`, `ollama` and `git` it runs outside the guard by absolute path, with their Homebrew kegs (the PATH dirs themselves stay open for `brew install` and `uv tool install`: the daemon runs with a system-only PATH and never looks a tool up by name);
    - the real target of any symlinked path in the profile;
  - read or write `runner.secrets_dir` (`~/.resonant/run-secrets`), `~/Library/Messages`, the Keychain files or any `runner.deny_read` path;
  - look up securityd (`com.apple.SecurityServer`, `com.apple.securityd*` and its agents; `trustd` stays, so TLS works), launchd, the Messages agents, Apple Events, LaunchServices, the window server, HID or accessibility; send Apple Events or open apps; open the HID drivers;
  - write auto-start entries: `~/Library` (LaunchAgents, login items), `~/.config`, `~/.claude`, `~/.ssh`, the shell and git startup files, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, the login-item store, the cron and at spools; or exec `launchctl`, `crontab`, `at` or the daemon's venv;
  - signal or take the task port of any process outside its own sandbox (the daemon, the kill switch), or reach port 7777 on any address.

  Hardlinking, renaming out, writing through a symlink and the `/.vol/<dev>/<inode>` path are all refused by the same rules (checked in the EM-1 spike). `resonant sandbox check` proves every deny and every owner-like allow after each OS update, and a self-probe (a write into `~/.resonant`, a securityd lookup, port 7777) fails closed before each run. Residual: a sandboxed process can read another same-user process's argv and environment, so no Resonant secret is put in one except the session's own Claude token; a run's GitHub token reaches the session through its credential-helper files, and repo keys through the checkout's `.env`.

## Health

- **Watchdog.** An asyncio heartbeat beats every second, and a separate thread calls `os._exit(1)` if it goes stale. launchd then restarts the daemon.
- **Dead-man switch.** The status relay ([`dashboard-plan.md`](dashboard-plan.md) D6, go-live step 15). While `relay.enabled`, the daemon pushes a `remote` snapshot to Supabase every minute, and the checker on Fly alerts the owner's phone (ntfy or a webhook, never through the Mini) when none has arrived for 5 minutes, when a snapshot reports a `failing` row, or when it can't read Supabase, and once more on each recovery. A whole-process freeze (SIGSTOP), a power cut, or a reboot waiting at the FileVault login all stop the snapshots. The older ping still works on its own: with `health.healthchecks_url` set, the daemon GETs it while the loop is ticking and POSTs `<url>/fail` with the reason when it isn't. `--check`'s advisory `dead-man switch` row passes with either.
- **iMessage self-test (Phase 1).** The health monitor runs it on its first round after start whenever it is due (none yet, older than 6h, or a failure older than 30 min) and re-runs it every 6h; a failure (AppleScript or the `chat.db` schema broke) degrades the `imessage` check. It sends a random nonce to Resonant's own handle and waits for the reader to see it; the result is kept in kv `imessage.selftest`. `resonant selftest imessage` runs the same check by hand, next to a live daemon.
- **Health monitor (Phase 1).** `resonant/monitor.py` evaluates `model`, `imessage`, `loop` and `store` every 60s, keeps an `ok → degraded → ok` state per check in kv `health.<check>`, and texts the owner over iMessage ("hey, some issues here: …", then "resolved: …"), at most once per check per 6h. Slack is never involved: it belongs to extensions. When iMessage itself is degraded, nothing is sent over it, and the dead-man `/fail` ping carries the reason as a plain-text body instead. State shows in `/api/status.health`, `GET /api/channels` and `resonant status`.
