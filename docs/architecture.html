Task lifecycle

Every task follows the same fixed lifecycle. The work itself is opaque: it lives in checkpoint and is owned by the runner. Each Runner.step commits its outcome, checkpoint, and consumed events in one transaction. If the daemon crashes mid-step, nothing from that step is saved, and the task resumes from its last checkpoint.

Wait reasons

  • approval: a gate decision is pending (L1, inferred L2, or anything above L0 under the kill switch), with wake_at = the expiry
  • veto: reserved for veto windows on unattended jobs (deferred past Phase 3); unused
  • human_reply: a Claude worker ran resonant ask, or a check that asks the owner (the run's own reason is question); the slot is freed and the answer resumes the same session (EM-3)
  • usage_reset: hit the Claude usage limit; parked until the reset
  • ci: an auto-merge waits for green CI, polled every 2 min for up to 2 h, with no inbound webhooks (EM-7)

Guarantees

  • An event for a waiting task requeues it.
  • An event that arrives during a step that returns Wait requeues the task right away, so no wakeup is lost.
  • A retryable failure backs off 5s·2ⁿ (max 300s) and keeps its events.
  • A step that runs longer than stuck_after_s is cancelled and retried.
  • Continue and Wait reset attempts.

Terminal states

  • done: the runner returned Done(result)
  • failed: a non-retryable failure, or attempts ran out (default 3)
  • cancelled: abandoned; for a Claude run this also removes its worktree or scratch dir and its run dir

Approval flow (text-reply over iMessage)

Built in Phase 2. A side effect that asks (L1 always; L2 when the model chose it; anything above L0 while the kill switch is on) parks the task in waiting(approval). Resonant texts the approver a short code: [A7] restart Resonant? Reply yes / no, or for L1 [D7] delete all 4 notes? This can't be undone. Reply yes D7 / no. Your reply binds to exactly one pending approval, or Resonant asks again; it never guesses. Phase 2 uses a deterministic parser only.

Deterministic parser

  • The whole message: yes|approve|👍 [code], <code> yes, no|deny|👎 [code], <code> no, yes [code] with comments: …
  • y, ok, sure and yes all are not replies; text that doesn't parse routes normally
  • Slash commands win first, so /kill is never read as a reply
  • A plain yes binds only when exactly one approval is pending; otherwise Resonant re-asks with the codes

Deferred

  • An approval classifier for free-form replies, and resonant eval approvals
  • Batch approvals (yes all)
  • Veto windows ("doing X unless you stop") for unattended jobs, deferred past Phase 3: asking jobs ask instead
  • See docs/followups.md

Money is stricter

  • pay tools are always L1, and that is enforced at registration
  • Like every L1 action, the only accepted reply is yes A7 with the code; a plain yes never approves it
  • The same rule applies on Slack: a typed code, not a button

Binding and audit

  • The reply must come from an approver handle (the owner for builtins); a non-approver always gets Nothing is waiting for approval.
  • Sent-before rule: the prompt must have been sent before the reply's occurred_at
  • Messages that arrive as SMS are dropped; only service='iMessage' counts
  • Each approval is tied to an intent_hash and expires after gate.approval_ttl_s (default 1800s); the task wakes at expiry and says so
  • Resolution is one conditional UPDATE, idempotent per event (resolved_event_id): a replayed or racing reply resolves once
  • Single use (used_at); a task that ends expires its pending approvals, so a later yes binds nothing
  • The audit row records the path, approved_by, and the code
  • yes with comments adds a human_input event that the runner sees as a constraint

Phase roadmap

Each phase ships before the next one starts. Phase 0 is built in one session to freeze the interfaces. Phases 1 onward are broken into Linear tickets one phase at a time (/linear-surf) and run with /robot-surf-fan. Claude work now follows the employee model (docs/employee-plan.md, EM-1..EM-9), which superseded Phase 5a; docs/phase5a-plan.md and docs/repos-plan.md are historical.

Trust model

Identity grants permissions. Content never does. Messages, emails, web pages, tool output and worker text are all untrusted input. Effect tiers come from tool registration, never from the model. The model never sees secrets. Claude workers run on standing trust above a hard floor: the thin guard protects Resonant itself, and everything else is an honor system shaped by trust rules (docs/employee-plan.md).
