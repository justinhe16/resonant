Task lifecycle

Every task follows the same fixed lifecycle. The work itself is opaque: it lives in checkpoint and is owned by the runner. Each Runner.step commits its outcome, checkpoint, and consumed events in one transaction. If the daemon crashes mid-step, nothing from that step is saved, and the task resumes from its last checkpoint.

Wait reasons

  • approval: a gate decision is pending (L1)
  • veto: an L2 veto window, with wake_at = the deadline
  • human_reply: an ask_human question was forwarded to a person
  • usage_reset: hit the Claude usage limit; parked until the reset
  • ci: PR opened; CI is polled on the tick via gh/API, with no inbound webhooks

Guarantees

  • An event for a waiting task requeues it.
  • An event that arrives during a step that returns Wait requeues the task right away, so no wakeup is lost.
  • A retryable failure backs off 5s·2ⁿ (max 300s) and keeps its events.
  • A step that runs longer than stuck_after_s is cancelled and retried.
  • Continue and Wait reset attempts.

Terminal states

  • done: the runner returned Done(result)
  • failed: a non-retryable failure, or attempts ran out (default 3)
  • cancelled: abandoned, which also triggers worktree cleanup (planned, Phase 5)

Approval flow (text-reply over iMessage)

Planned for Phase 2. A side effect at level L1 parks the task in waiting(approval). Resonant texts the approver a short code. Your reply binds to exactly one pending approval, or Resonant asks again; it never guesses. Pay approvals skip the classifier entirely.

Stage 1: deterministic parser

  • Matches yes / no / approve / deny / 👍 / 👎, case-insensitive
  • yes with comments: …
  • An optional code, e.g. yes A7; required when more than one approval is pending

Stage 2: approval classifier

  • Runs only if the parser fails. Separate from the router.
  • Input: only your reply plus the code-templated summary
  • Output: {decision, approval_code, comments, confidence}
  • Approves only if decision=approve ∧ confidence ≥ 0.9; anything else is unclear, so Resonant re-asks

Money is stricter

  • pay tools are always L1, and that is enforced at registration
  • The only accepted reply is an exact yes A7 that includes the code. No classifier.
  • The same rule applies on Slack: a typed code, not a button

Binding and audit

  • The reply must come from an approver handle, which must also hold can(…, 'approve', ext)
  • Messages that arrive as SMS are dropped; only service='iMessage' counts
  • Each approval is tied to an intent_hash and expires
  • The audit row records the raw reply, the path (parser or classifier), the confidence, approved_by, and the code
  • yes with comments adds a human_input event that the runner sees as a constraint

Phase roadmap

Each phase ships before the next one starts. Phase 0 is built in one session to freeze the interfaces. Phases 1 onward are broken into Linear tickets one phase at a time (/linear-surf) and run with /robot-surf-fan.

Trust model

Identity grants permissions. Content never does. Messages, emails, web pages, and tool output are all untrusted input. Effect tiers come from tool registration, never from the model. The model never sees secrets.
