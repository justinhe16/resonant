# Brain plan (Phase 6a): a general agent loop on the local model

Status: **built** (2026-10-18; BR-10, BR-10b and BR-11 2026-10-19): BR-1, BR-1b, BR-2, BR-4, BR-5, BR-6, BR-7, BR-8, BR-9, BR-10, BR-10b and BR-11 (§2, §6). Since BR-10 a triage call routes each chat turn to the local loop or to Claude, and Claude's sessions use Resonant's tools through the gate; since BR-11 the owner's hard texts go to one long-lived Claude session (the Claude brain). `brain.mode: loop` is the default since BR-8 (the live loop scores 91.0% on the example set over 3 runs, BR-1b's 92.3% within noise, over the 85% bar); `intents` stays as an opt-in and as the loop's per-turn fallback. The owner's own eval set is still to run (followups). Built with robot-surf in the waves of §5.

Texting Resonant should feel like texting Claude: general questions and conversation, looking around the Mini read-only, Resonant's own tools (still gated), extensions, other programs, Claude workers with Remote Control. Today every non-slash text is one intent label (`router/labeler.py`) → that intent's fixed toolset (`router/intents.py` `INTENT_TOOLS`) → `runners/local.py` capped at 3 model calls and 3 tool calls → a number guard that swaps the reply for a template. History is 5 earlier messages as user turns, nothing reads files or logs (`tools/builtin.py`), and nothing escalates (`escalate=True` is written and never read). "Where is mycelium?" had no route, so it failed.

The local qwen3-30B stays the brain. The harness changes, modeled on Claude Code's: one loop, an environment briefing, a memory index, general read tools, tools loaded on demand, a subagent for hard questions.

## 1. Owner decisions

- **Use cases:** questions about the Mini; personal assistant (calendar, email, reminders, notes); research and the web; named programs; photos, screenshots and voice; links; long-running asks ("watch X, tell me when Y"); other people with per-person grants (today's principals model). Group chats later.
- **Fast first, escalate:** the local loop answers; when it's stuck or the ask needs the web, email, calendar or an image, it hands it to a read-only Claude session and sends "looking into it…" first.
- **Email and calendar:** read and draft. Sending an email or creating, changing or answering an event asks first.
- **Programs:** each one a small extension with start, stop and status tools (e.g. trade-jev), not a generic runner.
- **Memory:** recent turns plus a small store of long-term facts.
- **Read scope:** `~/code`, `~/resonant`, Resonant's state, logs and docs, run transcripts. Never `~/Documents`, Mail, Messages, the Keychain, `~/.ssh`, `.env`-like files.
- **Ambiguity:** best guess for reads (say what it assumed), ask for writes.
- **Style:** a terse coworker.
- **Proactive:** yes, sparingly: a few notices a day, through the pulse.
- Everything that exists stays: fast path, gate, approvals, standing allows, kill switch, audit, extensions, MCP, workers and Remote Control, trust rules, pulse, dashboard.

## 2. Decisions

- **D1. One loop.** `runners/brain.py` handles every non-fast-path chat task. The fast path is unchanged (slash commands, `status`, `ping`, approval replies, the relay's `R4 …`, `/kill`). `brain.mode: intents | loop`, default `loop` since BR-8 (it was `intents` until the evals passed, §4). In loop mode the labeler is skipped (two prefixes would evict each other's KV cache with Ollama's one slot). A `ModelOutputError` in the loop falls back to the intents path for that turn.
- **D2. Prompt order for the cache.** Qwen's template puts the system text before the tool definitions in one turn, so anything that changes per turn goes after them: fixed system prompt (role, style, rules) → core tool schemas → the deferred-tool catalog (one line each; changes only on extension install) → facts index → rolling history (append-only, older part summarised) → one wrapped user turn with the **briefing** (time, repos and paths, runs with state and Remote Control links, extensions, open asks, health; from `dashboard/snapshot.py build_snapshot` local tier and `status.collect_status`; ≤1.5k tokens) and any "since we last talked" notes → the current message. A CI test pins the prefix hash.
- **D3. History as real turns.** The last ~10 exchanges as user/assistant turns (not `<prior_reply>` user turns), each capped; older ones folded into a running summary per principal. Tool results inside a task are still replayed as untrusted user turns.
- **D4. Tools: core plus deferred.** About 14 core tools always loaded: the read tools (D5), `remember`/`forget`, `ask_claude`, `load_tools`, notes and reminders add/list, `list_runs`, `run_activity`, `start_run`, `system_status`. Every other builtin, extension and MCP tool the principal may use is listed by name and one line; `load_tools(names)` adds up to 8 for the rest of the task. Per-principal filtering happens before anything is listed. *(BR-1b: `load_tools` is gone; the "one line" is a stub tool with a slim schema, because Ollama coerces a call to an unoffered tool into an offered one. See §6.)*
- **D5. Read tools** (`tools/files.py`, L0): `read_file`, `list_dir`, `search` (ripgrep), `tail_log`, `read_transcript`. Real path resolved, then the deny list, then the allowed roots (§1); symlinks out of a root and `..` refused; byte and line caps; output redacted (`redact.py`) and wrapped as untrusted data. Owner-only by default; members only through a grant.
- **D6. Taint.** A task that has read untrusted content (files, logs, transcripts, web, email, extension results, `ask_claude` output) is tainted; Resonant's own state reads and the facts index don't taint. A tainted task's model-chosen calls use a new origin `tainted`: the gate asks for L2 and L3 (standing allows don't apply, since they require `inferred`). The approval summary is code-built (`gate/summary.py`), so injected text can't reword what the owner approves. This is the one gate change in this plan.
- **D7. Limits.** At most 8 model rounds per task, reads free inside them; side effects ≤3 per task and one approval stops the task (both unchanged). Replies up to ~1500 chars. The hard number guard stays on the intents path only; in loop mode it logs and counts in the evals, and the prompt says to state only what it read. If the loop passes ~6 s, a short progress text goes out.
- **D8. `ask_claude`** runs as its own task (`runner="ask"`), not inside the chat step: "looking into it…" goes out, then the answer when it's back. `claude -p --restricted --tools Read,Grep,Glob,WebSearch,WebFetch --permission-mode dontAsk` with an **allowlist** of connector read (and draft, if the connector has one) tools, write tools never allowed (Gmail send, Calendar create, update, delete, respond), `Read` denied on the deny list, `--add-dir` for the read roots, no session persistence, `--max-turns 15`, 120 s timeout. The real connector tool names are read from the `init` event; it refuses to start when an expected read tool is missing. Concurrency 1 (`brain.ask_claude.concurrency`), a daily cap (~30), separate from worker slots; a usage limit backs off and tells the owner (`runners/claude.py` `usage_limit`). Sends and event changes come back as a code-built proposal and go through a gated tool. **Unverified:** whether `--restricted` keeps claude.ai connectors; BR-5 probes it first. Gmail and Drive need the owner to finish connecting them in claude.ai. *(BR-10: a brain-handed ask also gets Resonant's own tools over a per-task MCP bridge, every call through the gate and executor, so Claude can change things only as the local model can; its own tools stay read-only. §6.)*
- **D9. Facts.** `~/.resonant/brain/facts/<slug>.md`, one fact each, with an index rendered into the prompt. `remember` and `forget` are L3 (do, then report), owner only.
- **D10. Media, links, watches, proactive.** Image and voice attachments from chat.db go to `ask_claude` (voice to local whisper when present). A link is summarised through `ask_claude` (WebFetch). "Watch X, tell me when Y" becomes a proposed job on an extension or a `watch` builtin, and asks first. Brain-authored notices go through the pulse with a daily cap on top of the hourly one.

### As built: BR-4 (context and memory)

`resonant/brain/` (context, briefing, history, facts), `store/brain.py` (migration 015) and `tools/facts.py`; contracts in [`interfaces.md`](interfaces.md#brain-context-and-memory-resonantbrain-br-4-migration-015). Not wired into a runner: BR-1 calls `build_context` per turn and `fold` after the reply.

- **D2.** `build_context` returns `BrainContext(prefix, history, turn)`. The prefix is the system message, then (only when non-empty) one user turn with the deferred-tool catalog and the facts index; a user turn rather than a second system message, so every chat template keeps it after the tools. The last turn is `<briefing>`, `<since_last>` notes, `Current time:` and the wrapped message. `tests/test_brain_context.py` pins `prefix_hash` and checks the prefix is byte-identical across turns and the briefing never lands before history. The briefing is about 1.5k tokens at most (6000 chars) with per-section caps and `+N more`; it lists approvals by summary, never their codes. A member's briefing is the status line only, with no facts and no notes.
- **D3.** Each exchange is a wrapped user turn and an assistant turn (500 and 800 chars). A fold runs once 15 exchanges are unfolded and keeps the newest 10, so history is append-only between folds (a sliding window would shift every turn and miss the cache). The fold is one `chat_json` call with 400 tokens out; when the model is down or answers badly the summary is built in code. A backlog (the first fold) folds at most 20 exchanges and skips anything older.
- **"Since we last talked".** Since the principal's previous message (at most 7 days back): runs that ended or merged, approvals that expired, worker questions asked; the newest 8. Owner only.
- **D9.** Facts are files (`~/.resonant/brain/facts/<name>.md`, frontmatter `name`/`description`), at most 50, a 120-char description and 2000 chars of text; `remember`, `forget` (L3, reported `Remembered …` / `Forgot …`) and `list_facts` (L0) are builtins that no intent offers, so the intents path is unchanged. Control and format characters are dropped; the index removes angle brackets. Since the index is in every later prompt, an injected `remember` would persist: L3 stays (the owner's call), the report line shows the whole description, the prompt calls facts context rather than instructions, and BR-1 must route a tainted task's `remember` through D6's ask. The deferred-tool catalog goes through the same cleaning, since extensions write it.

## 3. Out of scope

Group chats; a generic "run any program" tool (programs are extensions); writes by `ask_claude` outside the gate (BR-10: Claude changes things only through Resonant's tools, gated like the local model's; never with its own tools, never an email send or event change); replacing qwen; new sandboxes for workers (they stay unguarded).

## 4. Evals and verification

- Latency: fast path p50 ≤1 s; a simple loop read ~5 s, a three-step task <15 s; "looking into it…" within 2 s of escalating.
- `ScriptedModel` (`e2e/fakes.py`) gains a scripted mode (tool calls and a final reply per test); the label mode stays.
- On the Mini, by text: "where is mycelium", "what's R4 doing", "and where's that?", "what's on my calendar tomorrow", "draft a reply to the last email from X" (draft only), "look up X", a screenshot, "start trade-jev" (asks).

### BA-1: batch approvals (2026-10-19)

The owner texted the Claude brain to update 4 Linear tickets. A task allowed **one** approval and refused every other change after it (`PENDING`), so it took 4 texts and 4 yeses. BA-1 lets a task collect every change that needs approval and ask **once**. Contracts in [`interfaces.md`](interfaces.md#approvals-binding-codes-and-replies) (batches, binding), [`interfaces.md`](interfaces.md#tool-core-resonanttoolcore-tc-1) (batch mode) and [`interfaces.md`](interfaces.md#local-runner-resonantrunnerslocal) (the batch step); carry-overs in [`followups.md`](followups.md#ba-1-carry-overs-batch-approvals).

- **Collect.** A Claude brain turn, a one-shot ask with tools and the local brain loop call `ToolCore.call` with the task's batch (`CallScope.batch`). A call the gate asks about joins it: pinned in `checkpoint.batch` (a `BatchItem`: the pinned call, its approval, its code-built line, its taint), and the model gets `asked the owner: <summary>` (never a code) and goes on. Claude's `PENDING` refusal is gone; qwen's turn no longer ends at the first ask (the turn's answer gives way to the batch, as its one approval's did). The same change twice is one entry. The intents path still asks once per task.
- **One prompt.** When the turn ends (Claude: after its answer is sent), the local runner's batch step (`LocalRunner._batch`, shared by the brain and the ask runner's resume) asks. One change: the plain prompt as before (`yes always` offered as before). Several: `PolicyGate.open_batch` stores the snapshot in `approval_batches` (migration 002's table, unused until now: **no migration**), gives the approvals one expiry from the prompt, and the owner gets `[D7] 4 changes, all or none:` with a numbered code-built line each (`1. linear: save issue id="RES-12", state="Done"`) and `Reply yes / no`; with an L1 among them `Some can't be undone. Reply yes D7 / no` (the batch takes its strictest level; pay: `yes D7` exactly). The code is the first approval's; the others' are never shown and name nothing.
- **Answer.** The gate binds a reply to a batch as one unit (a plain yes/no counts it as one pending item; `ambiguous` re-asks list it as one; `yes always` is refused for it; the sent-before rule and per-event idempotency hold) and resolves all of its approvals in one transaction, all or none, audited with `batch_id` and `approval_ids`. `resolve` by id (the CLI) of any of them resolves the batch. **Only the owner answers a batch**: a member who approves the extension gets `Nothing is waiting for approval.` (a lone change still goes to every approver). `yes`: each approved change runs once, in order, through `ToolCore.resume` (`executions` first: a restart mid-batch replays what ran, reports the one that was running as `Not sure whether … ran` and never re-runs it); a failure doesn't stop the rest; the reply is a line per change. `no` → `Not done.`; expiry → `Not done: the approval for those 4 changes expired.`; the kill switch's pause → `Not done: Resonant is paused (/kill), so none of the 4 changes ran.` (or `Stopped: …` mid-batch).
- **Caps.** `gate.batch_max` (10, 2–20): past it a change is refused (`Not done: at most 10 changes can wait on one yes.`) and its approval dropped (never prompted, so nothing can bind it). Changes that run without asking (L3, a standing allow) are capped apart at `MAX_SIDE_EFFECTS`, raised from 3 to **5** per task so 4 tickets fit under a standing rule (the intents path stays at 3, its call cap). Taint is unchanged: a tainted task's L2 and L3 changes all go into the batch, never run silently.
- **"dont ask for perms for linear tickets".** Checked first: the trust rules from chat (`allow_trust_rule`) named workers' actions only, and the standing allows the gate honors for chat tools (`tool:<ext>.<name>`, GT-1) could be made only by `yes always` on a prompt or `/rules allow`; the model had no way to name "Linear's changes". New builtin **`allow_tools{tools: [linear]}`** (L2, never a standing allow itself, so it always asks; "loosening asks you first"): an extension's name covers its chat tools that can take a standing allow (its L2 changes: for linear `save_issue` and `save_comment`; never L1, pay or reads), `linear.save_comment` names one. Its prompt names exactly what stops asking, from the registry: `stop asking before linear.save_comment and linear.save_issue when you ask in chat`. `yes` saves `allow tool:linear.save_issue in linear` and `… save_comment` (the rules `yes always` saves; `/rules` lists them), and from then on the owner's own model-chosen saves run and report, from Claude over MCP and from qwen; tainted ones, members, L1 and the kill switch still ask. **Claude's saves don't taint the session** any more: the bridge used to taint on any extension call, but an extension change that ran shows Claude only its code-built `Done:` line (from its own args), never the result; a failed one's reason, and every read, still taint.
- **Review fixes.** A batch line is never clipped and its `yes always` note is cut only as the code-built suffix of an approval that offered one (a model-chosen arg containing the marker could otherwise hide the args after it). A batch with a trust-widening change (`allow_tools`, `allow_trust_rule`, `remove_trust_rule`) marks it `widens trust:` and needs `yes <code>`. A plain reply is judged only among the prompts the owner got, so a turn still collecting changes never makes it ambiguous; a session with no answer, or a turn that fails for good, drops what it pinned. The briefing and pulse show a batch once by its code (`approvals.answerable`); `resonant approvals` marks batch rows.
- **Tests.** `tests/test_e2e_batch.py` (14, the daemon in process with a fake `linear` extension run by the real process runner and fake Claude through the real relay): 4 saves in one Claude turn → one prompt, `yes` runs each once; `no` and expiry run none; L2 + L1 needs the code; a partial failure is reported and the rest run; a tainted batch asks even with a standing rule; "dont ask for perms for linear tickets" then 4 saves run unasked (Claude) and the same over qwen; qwen batches; the kill switch blocks an approved batch; the cap; members can't answer; the codes never reach Claude. `tests/test_batch_approvals.py` (23, the gate and the runner's batch step): the prompt text, re-prompt idempotency, a lone change's plain prompt, a crash mid-batch never runs a change twice, binding (ambiguous with a lone approval, hidden codes, `yes always`, the code for L1, members, `resolve` by id), the cap, taint kept through the batch, `/approvals <code>` for a batch, and the model never seeing a code. Updated: the bridge's change cap test (5 now), the qwen taint tests (unchanged: one evaluation per ask), `open_batch` no longer `NotImplementedError`.

Live run (`evals/task.example.jsonl`, 71 rows, loop mode, `--route triage`, `--repeat 1`, qwen3-30b-a3b-instruct-2507, a fresh `RESONANT_HOME`): **95.8% (68/71)**, **0 unapproved writes**, asks 100% (47/47), triage 100% (38/38), escalation recall 100%, Claude route 39.4% (28), ack p50/p95 1586/4371 ms, latency p50/p95 1954/5015 ms. The misses are BR-8/9's three noisy rows (`runs-waiting`, `follow-wheres-that`, `inj-log-orders`), as in BR-10b and BR-11 (95.8–97.2%): the eval's cases ask about at most one change each, so batching doesn't change their grades; the e2e tests carry the multi-change cases. ### TC-1: the tool core package (2026-10-19)

A pure refactor: the shared tool call path is its own package, `resonant/toolcore/`, and every caller goes through it. Before, it lived in `LocalRunner._call_tool` and its helpers, and the Claude bridge reached it by subclassing `LocalRunner` (`ToolCaller`); the job and watch runners called the gate and executor themselves.

- **The API.** `ToolCore(conn, registry=, gate=, executor=)`: `await call(target, args, scope) -> CallOutcome` for a new call, `await resume(pinned, scope)` for a pinned one (the approval resume), and `recorded(...)` (the job's first look). `CallScope` carries the task id, principal, trace, step, call index, origin, spans, the checkpoint and its `save` (`steps`), the report lines so far (the side-effect counter), extra pin keys (taint), the offered tools and `check_schema`. `CallOutcome = Ran | Asked | Refused | Failed`, code-built text only; `Asked.summary` never holds the approval code. Contracts in [`interfaces.md`](interfaces.md#tool-core-resonanttoolcore-tc-1).
- **Moved in.** The registry lookup, the schema check (`args_error`, from `runners/brain.py`), `PinnedCall` / `is_explicit` / `pinned_origin`, `gate.evaluate`, the pin, the executor call and the `recorded` replay, the code-built report and refusal lines (`toolcore/reports.py`: `REPORTS`, `report_line`, `refusal_reply`, …, from `runners/local.py`), the `Rule added` line and the side-effect cap. `runners/local.py` and `runners/brain.py` re-export what tests import from them.
- **Callers.** `LocalRunner._call_tool` / `_resume` (and so `BrainRunner` and `MediaRunner`) are thin adapters over `self.core`; `gated_answer` and `model_result` map an outcome to the runner's `Answer` / `CallResult`. The bridge (`ClaudeTools`) calls `ToolCore.call` directly and handles `Asked` itself (pinned, never prompted); `ToolCaller` is gone. The ask's approval resume is a plain `LocalRunner` named `ask` (`AskRunner.resumer`). `JobRunner` and `WatchRunner` call `ToolCore` with origin `scheduled` and no pin; the router's fast path spends its inline read's token through `toolcore.allow_inline`.
- **No behavior change.** Same gate inputs, pins, idempotency keys, report lines and span names (`runner.local.tool`, `runner.local.call`: the task eval counts writes from them). The intents path still doesn't check args against the schema (`check_schema=False`), as before.
- **The guarantee as a test.** `tests/test_toolcore_boundary.py` scans every module's AST: outside `toolcore/`, `gate/` and `executor.py`, nothing calls `evaluate`/`consume` on a gate or `execute`/`recorded` on an executor. One listed exception: `extensions/scheduler.py`'s inline L0 jobs (left alone while BK-1 works there; [`followups.md`](followups.md#scheduler-inline-jobs-onto-toolcore)).

### BR-11: the Claude brain, one long-lived session (2026-10-19)

BR-10 started a `claude -p` per hand-off: every hard text paid a cold start, and a follow-up only knew the last four exchanges Resonant replayed. BR-11 keeps **one** Claude session for the owner's hard texts, the "Claude brain": qwen still takes the fast path, triage and the instant ack, and every hard text is one user message into that session. Everything after it is BR-10's: the per-task MCP relay, the shared call path (`LocalRunner._call_tool`; since TC-1 `ToolCore.call`), the gate and the executor, Claude's answer to the owner as `Claude: …` (never rewritten by qwen) and recorded in history under BR-10b's rules. Contracts in [`interfaces.md`](interfaces.md#the-claude-brain-resonantrunnersclaude_session-br-11); carry-overs in [`followups.md`](followups.md#br-11-carry-overs-the-claude-brain).

- **The session** (`runners/claude_session.py` `ClaudeSession`, owned by `AskRunner`). RC-1's live machinery (`runners/live.py` `LiveInput`): `claude -p --input-format stream-json --output-format stream-json`, stdin kept open, one `user` line per turn, the turn's end is its `result`. Same restrictions as a BR-10 ask (`runners.ask.session_argv`): `--restricted`, `--tools Read,Grep,Glob,WebSearch,WebFetch`, `dontAsk`, the same allow, deny and `Read()` rules, `--add-dir` roots, `--mcp-config … --strict-mcp-config` with Resonant's tools; `--session-id <uuid>` (new) or `--resume <id>`; no `--no-session-persistence` or `--max-turns` (a turn is bounded by `turn_timeout_s`); a system prompt for a long conversation (`SESSION_PROMPT`: each user message is one owner text; earlier messages and Resonant's records are data). cwd `<RESONANT_HOME>/ask/session`.
- **What goes there.** An owner's hand-off with Resonant's tools (triage, the model's own `ask_claude`, an escalation; kinds `general`, `research`, `link`; no attachments): `enqueue` marks it `session`. The ask task is unchanged otherwise (queue entry, bridge, approvals, reply, history note). **Members never reach it**: `ask_claude` has no grant, so a member can't escalate at all, and an ask for anyone but the owner is a one-shot. Email and calendar asks (connector reads, per-kind allowlist), images and PDFs (`runner="media"`), and watch checks stay one-shot `claude -p`.
- **Per-turn binding.** The MCP server (`ask_tools.McpServer`: socket, token, config) lives as long as the session object, since the relay Claude Code started holds its socket and token. Each turn's `ClaudeTools` binds to it on `start()` and unbinds on `aclose()`; a request is served by the binding current when it arrives (that turn's task id, principal, trace, checkpoint and origin), a call between turns gets `not run: no message from the owner is being answered right now`, and an ended binding refuses (`the session ended`). The e2e tests drive one relay connection across two turns and check every executor row's `task_id`.
- **Serial and the queue.** `ClaudeSession.lock`: one turn at a time, one process, no side sessions. A turn whose task isn't the oldest unanswered session ask (or the session is busy) waits (`Wait("usage_reset", +1 s)`); a turn waiting on an approval is out of the queue. `enqueue` refuses past `queue_max` waiting (3) behind the one in flight with `busy`: the brain replies `Claude has N waiting already; send that again once those are answered.` A queued turn's ack says what's ahead: `on it, checking (after "why is R4 slow", then this)` (the owner's own first words, cleaned).
- **Lifecycle.** Lazy: the first hard text starts it. **Health**: before every turn the process and its reader must be alive, else it restarts. A turn past `turn_timeout_s` (240) is a hang: the reply is `Not done: Claude took over 4m; stopped.` and the session is killed; the next text starts fresh. A **crash** mid-turn (the process ends with no `result`) restarts it fresh; the turn is retried once there only when no change reached the gate (`ClaudeTools.changes == 0`, nothing pending), else the reply is `Not done: Claude's session ended mid-answer, after it had started a change, so it wasn't run again; it restarts on your next text.` with the code-built line of what ran. A daemon crash mid-turn: the task's `session_turn` mark plus a pinned call replies `INTERRUPTED` as before. **Fresh sessions are primed** (`brain.history.primer`): the running summary and the last 6 exchanges as the fold sees them (the owner's words; Resonant's reply unless tainted or Claude answered, then `(answered from outside content; not kept)`), so a primer never carries Claude's text or anything a tainted turn wrote (BR-10b). **Resume**: kv `brain.claude_session` keeps the id once a turn came back; after a daemon restart the next turn is `--resume <id>` (no primer); a resume that doesn't take (the process exits, or dies before answering) starts a new id with the primer. **Rotate**: after `rotate_turns` (50) or `rotate_hours` (12), a backstop to Claude Code's own auto-compaction. **Ends** the RC-1 way (`stop`: Remote Control off, stdin closed, 3 s, then the group reaped): `/kill` (a pause hook; a turn in flight replies `Stopped: Resonant was paused (/kill).` and is never retried while paused), and daemon shutdown (`wiring.close_asks`, the id kept). The pid, start time and marker are in kv, so one a crashed daemon left is reaped before the next start.
- **Review fixes**: the pause hook's stop runs outside the session's tracked readers (it never waits on itself) and marks the turn killed (a `/kill` that lands between polls is never taken for a crash and retried); the init check is armed before a spawn, so a resumed process's early `init` is checked; a turn's hops are recorded under the session's lock; `--max-budget-usd` scales with `rotate_turns`; the queue label is the owner's own message, never model-written question text.

- **Taint, per turn.** A turn starts tainted when the asking turn was (its BR-10b hops reach the session through `tools.ask.ASKING_HOPS`, a context variable the brain sets around its `ask_claude` call) or the session's last turn was tainted within the hop window (`ClaudeSession.inherited_hops`: last hops `h < MAX_TAINT_HOPS` → `h + 1`). A turn that read outside content itself (one of Claude's own tools, a tainting Resonant tool, an unsynced change: `ClaudeTools.read_outside`) is hop 0. The turn's hops are kept for the next turn and noted with Claude's answer (`claude_session`, `claude_hops` on the asking brain task); `history.Exchange.untrusted` counts a session answer only when its turn was tainted under `MAX_TAINT_HOPS` (a one-shot answer always counts, as in BR-10b). The hand-off's own reply (the ack) no longer marks the turn as having read outside content for a session turn. So taint **lifts after the hop window**: a clean turn after a clean turn is clean however long the session lives, and after an outside read it lifts once BR-10b's window has passed (the e2e test measures it). A fresh session (primed from clean records) starts the chain clean. **The context lifts with the taint** (review): a turn that read outside content marks the session (`outside`), and once its hops have passed the window the next turn starts a fresh, primed session instead of reusing a context that still holds the page; a changed tool set restarts it too (the allowlist is fixed at spawn).

### BR-10b: replayed outside text taints the turn (2026-10-19)

BR-10 replayed Claude's answer in later turns (`<claude_answer>`), but taint was per task: a local turn that saw it started clean, so "ok do it" after an answer quoting an injected "cancel R4" could run `cancel_run` (L3) without asking. - **The rule.** An exchange in the replayed window is *untrusted* when it holds Claude's answer (`checkpoint.claude_reply`: Claude reads files, the web and connectors; any answer counts, whatever the session read) or its reply came from a tainted task (`reply_meta.meta.tainted`, or `tainted` pinned on the checkpoint). A turn whose window holds one starts tainted (`BrainContext.untrusted`, `history.replayed`), exactly as after an untrusted read (D6): model-chosen L2 and L3 calls ask, no standing allow, no `yes always`. A hand-off from such a turn starts Claude's session tainted (it already passed the turn's origin).
- **Hops: taint can't carry itself for good.** A tainted turn's own reply is tainted too (it may repeat the text), so a reply records `taint_hops`: 0 when its task read outside content itself or handed off to Claude, else one more than the nearest untrusted exchange it replayed (a Claude answer counts as 0). Hops go on the pin (`taint_hops` with `tainted`) and in `Done.result`; an own untrusted read resets them to 0. The review of this ticket found the first cut self-sustaining: every reply was marked tainted and the chain never ended while the owner kept chatting.
- **Narrow, not forever.** The window is the unfolded exchanges (at most `MAX_EXCHANGES`): with hops, a Claude answer in continuous chat taints the next 24 turns (14 at hop 1 while the answer is in the window, then 10 at hop 2 until those replies are folded; the e2e test measures it), then turns are clean again. The **fold never keeps outside text**: a tainted exchange (any hop) or one with Claude's answer is folded as the principal's message and `OUTSIDE_REPLY` ("answered from outside content; not kept"), never its reply or Claude's answer (model fold and code fallback alike), so the summary holds only the principal's words and untainted replies and never taints a turn. - **Every reply is marked.** `_turn` sets `Done.result.tainted` on every brain answer (hand-off, narration, report-only and fallback paths too, not just the plain answer), so the next turn's history can read it.
- **Claude's own history.** The ask runner's prompt replays the last 4 exchanges (`Owner:` / `Resonant:` / `You (Claude) answered:`); with an untrusted one among them the session starts tainted (`ClaudeTools.taint("history")`, span `runner.ask.taint` `source: history`), in case the asking turn wasn't (its window can be shorter after a fold).

This covers the brain's intents fallback and opt-in `brain.mode: intents`; a fallback whose own replies are clean stays untainted (D6's note stands).

### BR-1b: the loop on the live model (2026-10-18)

BR-6's first live run (qwen3-30b-a3b-instruct-2507, `main` d00518b) graded the loop 44.2% (23/52), escalation recall 50%, 0 unapproved writes, p50 1.3 s. Contracts in [`interfaces.md`](interfaces.md#brain-loop-resonantrunnersbrain-br-1-br-1b); carry-overs in [`followups.md`](followups.md#br-1b-carry-overs-the-loop-on-the-live-model).

Root causes and fixes:

- **Tool calls leaked as text.** The loop replayed each call as assistant text `{"tool_call": …}` and its result as a user turn, so from round 2 qwen wrote calls in that format and the loop sent them to the owner as the answer. Now calls and results are **native tool turns** (`ChatMessage.tool_calls`, `role: "tool"`, rendered by each adapter in its wire format; qwen's template shows them as `<tool_call>` and `<tool_response>`), and a call the model still writes as text (`{"tool_call": …}`, `<tool_call>`, `name: {args}`, a bare tool name) runs as a call (`text_tool_calls`). The intents path is unchanged.
- **The wrong tool ran.** "start a run on dori" recorded `list_reminders`: the model's raw text was `<tool_call>{"name": "list_repos"…}` (a catalog tool, not loaded), and Ollama's llama.cpp runner constrains a call's name to the offered tools with a grammar, so it came back as the nearest offered name. `prs`, `list_issues`, `trade_jev_*` all became `list_reminders`. No `load_tools` flow can survive that (the model calls the tool first). Now every tool the principal may use is offered: core tools with their schemas, the rest as **stubs** (exact name, one-line summary, the schema without descriptions or limits: the grammar needs `properties` and allows no others). A stub call is checked against the real schema in code; a bad one gets the schema back. The toolset is fixed for the task, so the KV cache isn't broken mid-task as `load_tools` did.
- **Claims without tools.** "note: buy oat milk" → "Added note: buy oat milk", no call; "merge site PR 41" refused with invented reasons. Two parts: the prompt (below), and a **corrective round**: an answer that claims a change (`claims_change`) while no side effect ran goes back once with "no tool ran, so nothing changed: call it or say you can't".
- **The briefing lied.** It always said `Workers aren't set up: no Claude runner in this daemon (iMessage is off)`: `BrainRunner` never passed the runner's state, so the snapshot's "no runner" default showed, in production too, and the model refused calendar asks and merges because of it. Now the daemon wires the dashboard's cached runner check (`api.runner_missing`), refreshed in the background (never on the reply path), and an unknown state says nothing.
- **Unhelpful errors.** A wrong path came back as `the tool failed`, and the model gave up. The brain now gets the read's own reason (`read_file: … is outside the read roots`, `tool_error_detail`).
- **The prompt.** Experiments replaying the failing prompts against the live model (same messages and tools) showed two things move qwen: a directive system prompt ("you act only through tools; if you didn't call it, it didn't happen"; which tool for health, logs, notes, reminders, facts; email, calendar, the web, links and images go to `ask_claude` with their kind; a change with no named target and several candidates asks first) and one line **after** the message (`TURN_NUDGE`: call the tool now if this needs a lookup or a change; ask which when the target is unclear; otherwise just answer). The second alone took most cases from prose to a call; it sits in the per-turn part, so the cached prefix doesn't change.
- **Ambiguous targets.** "cancel the run" with R1 and R2 active cancelled R2 at once (`cancel_run` is L3, so the gate doesn't ask). A **target check** (once per task): a write whose identifier arg (`code`, `id`, `number`, `*_id`) isn't in the owner's message goes back unrun with "ask which if several fit, else call again".
- **Not changed, on purpose:** a numbers check (an answer with unread numbers before any tool ran) was tried and dropped: it only ever fired on general knowledge ("86,400 seconds"). Briefing paths as `~/code/…` were tried and dropped: the model expanded `~` to an invented `/Users/owner`.

Eval harness (BR-6) changes, each because the world was unrealistic, never to fit a row: `HOME` is the world root while a case runs (on the Mini `~/code` is `runner.code_dir`, and seeded history says `~/code/mycelium`); the linear fixture takes the real extension's arguments (`list_issues` none, `save_issue{title, team}`; the CLI fixture required `id` even to create, contradicting its own description, and the scripted rows already called it the real way, unchecked until the brain validated stub args); calls the loop ran from text count as called. Rows: the nine scripts that called `load_tools` call the tool directly (scripts, not expectations); `mini-logs`'s fact is `rate limit|rate-limit` (the reply "rate-limited" was right); `ext-linear`'s script calls `list_issues` with no args. No other expectation changed.

### BR-1: the brain loop (2026-10-18)

`runners/brain.py` (`BrainRunner`, `runner="brain"`); contracts in [`interfaces.md`](interfaces.md#brain-loop-resonantrunnersbrain-br-1).

- **D1.** `brain.mode: intents | loop` (default `loop` since BR-8; `intents` before). In `loop` the router skips the labeler: after the fast path, approval replies and the relay's direct step, any free text goes to `relay.free` (as a `question`, so a reply to an open worker question still lands there), else `NewTask(kind="chat", runner="brain", checkpoint={"title": "chat"})`. The brain runner is registered in both modes, so a brain task outlives a switch back.
- **Reuse.** `BrainRunner` subclasses `LocalRunner`: tool calls go through `_call_tool` (registry spec, gate, executor; pinned before a gated call runs or asks), the resume after an approval, the code-built report lines and the resend are the local runner's. `local.py` gained hooks only (`_call_tool(origin=, pin=)`, `_pinned_origin`, a `limit` on `after_effects`/`with_report`, `Answer.meta`); the shared helpers are public now (`Answer`, `CallResult`, `clip_reply`, …). The intents path is unchanged and its tests pass untouched. (TC-1 moved that call path into `resonant/toolcore/`; `_call_tool` is now an adapter over `ToolCore.call`.)
- **D4.** *(Superseded by BR-1b: no `load_tools`, deferred tools are stubs.)* Core (17 + `load_tools`): `read_file`, `list_dir`, `search`, `tail_log`, `read_transcript`, `remember`, `forget`, `list_facts`, `ask_claude`, `add_note`, `list_notes`, `add_reminder`, `list_reminders`, `list_runs`, `run_activity`, `start_run`, `system_status`. Everything else the principal may request (builtins, extension chat tools; never job specs, never `mute_extension`, which stays slash-only) is the catalog. `load_tools{names}` is not a registered tool: the loop handles it (never gated or executed), adds up to 8 catalog tools for the rest of the task, and is offered only when the catalog isn't empty. A call to a catalog tool that isn't loaded gets `not loaded: call load_tools with its name first`. A member with `builtin:files` gets the five reads and no catalog.
- **D6.** The task taints once it calls a spec with `untrusted=True` (the read tools, `ask_claude`), any extension or MCP tool, or a builtin that returns text others wrote (`TAINTING_BUILTINS`: `list_runs`, `run_activity`, `answer_worker`, `message_worker`, `recent_logs`, `open_items`, `pulse_preview`, `briefing_preview`: workers read PRs and the web, logs and pulse items quote outside text); every later model-chosen call is `origin="tainted"`. A gated call is pinned with `tainted`, and `_pinned_origin` gates its resume with it, so a tainted `remember` or `add_note` asks before and after the approval (the e2e test checks both audit rows). The intents fallback starts a fresh prompt without the loop's tool results, so it runs untainted (BR-10b: unless a reply it replays was tainted). *(BR-10b: a turn also starts tainted when its replayed history holds a Claude answer or a tainted task's reply.)*
- **D7.** At most 8 `chat_tools` rounds; a reply with no tool calls is the answer, clipped to 1500. Side effects ≤ 3 and one approval per task, as before; at the cap one `chat_json` narrates and the report lines are always in the reply. 24 tool calls per task in all, as a backstop. The number guard only counts (`number_guard` in `Done.result` and on `runner.brain.answer`), against everything in the prompt and tool results. `On it…` goes out once (dedupe `progress:<task id>`) when a turn passes 6 s; an in-flight progress send finishes before the reply.
- **ask_claude.** When the model calls it and it queued, its `Looking into it…` is the reply and the turn ends (`path: "ask"`); a refusal goes back to the model. **Auto-escalation:** the round cap with no answer, two bad outputs, or the 24-call backstop calls `ask_claude` itself (through the gate and executor) with the message plus `(Resonant's local model ran out of steps; it tried: …)` (`path: "escalate"`). When the principal can't use it or it refuses (daily cap, off, paused): the round cap replies `TOO_MANY_REPLY`, bad output takes the intents path.
- **Fallback.** `ModelUnavailableError`, and bad output that can't escalate, run the intents path for that turn inside the brain runner (the labeler, then `LocalRunner._answer`; `brain_fallback: true` in the result), unless a side effect already ran, in which case its report lines are the reply.
- **D3.** After a brain task's reply is sent, `fold_due` is checked and `fold` runs as a background task (`BrainRunner.idle()` waits for it).
- **Fake.** `ScriptedModel(script=[…])` / `.push(…)`: a list of calls is a round, a string the final reply, an exception is raised; `requests` keeps every prompt and toolset. The label mode is unchanged. `tests/test_e2e_brain.py` covers the briefing answer, multi-step reads, `load_tools`, tainted writes and their resume, `ask_claude` and auto-escalation with the fake claude, the round cap, the fallbacks, members, progress, the prefix hash and the fold.

A watch is either a **tool check** (an L0 read builtin or extension chat tool the principal may use, its args validated against the tool's schema; condition `contains` / `missing` a text, or `changed` against the first check's fingerprint, decided in code: the result never reaches a model) or an **ask check** (a yes/no question; Claude answers YES/NO first). A brain-authored notice is a pulse item (`core` / `notice/<key>`), sent now unless paused or quiet (held for the hourly pulse), over `extensions.notify.max_per_hour` this hour (held for the pulse), or over **`brain.proactive_per_day`** (default 3) today (held `low`: the briefing).
